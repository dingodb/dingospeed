## 0. 这份文档怎么读

### 0.1 与既有文档的关系

这是**第三份增量需求**。主文档与批量增量的全部约束**继续有效，且一律不放宽**：命名空间强制、路径安全矩阵、摘要必填、内容按摘要寻址、回环监听、防淘汰、下载侧原样复用、快照标识由清单确定性计算、不建独立进度状态、发布是合并语义。

出现冲突时以既有文档为准，除非本文档在【本期修改】中明确写出。

标记规则沿用：**【硬性约束】** 不可协商，**【明确不做】** 是范围边界，**【待决】** 是需要产品/架构拍板后才能动工的点（汇总见 §13）。

### 0.2 一句话总结

> 这个增量的本质是：**把上传的"发起方"从人和脚本换成 spinfield 后端，并给这件事套一层可观测、可续跑、可原子提交的任务壳。**
>
> 内容落盘、摘要校验、断点续传、清单合并、快照标识计算、原子生效——**这些一行都不该动**。变的是**谁触发**、**过程怎么被看见**、以及**字节从哪读**（见 §3.1.1 的模式选择）。
>
> 用户的文件本来就在 dingofs 上，前端提交的是路径而不是内容——**前端到后端这一跳不搬运大文件**，这是整件事的出发点。
>
> 如果你发现自己在重写落盘逻辑或者重新设计清单格式，方向就错了。

### 0.3 动工前置条件

- `go build ./...` 与 `go test ./...` 可正常运行，既有环 1~环 6 的自动化断言**不得修改**。
- 每进入一个新环之前与完成之后，都必须保持上述基线。

## 1. 背景与目标

### 1.1 背景

当前 dingospeed 的本地入库能力（`dingo-local` 命名空间）已经完整可用，但它的使用形态是**人在服务器本机敲 curl 或跑脚本**：

- 调用方自己遍历目录、自己算 SHA-256、自己攒发布清单、自己处理中断重跑；
- 没有权限概念，只有一个全局共享 token；
- 没有任务概念，进度只能靠调用方自己 N 次查询 `local-upload-progress` 拼出来；
- 出了问题只能翻服务端日志。

spinfield 是面向使用者的模型仓库管理平台，具备用户体系、仓库权限、仓库状态与版本管理。要让内部用户在 spinfield 上"点一下就发布一个模型版本"，就需要把这两侧打通。

### 1.2 现状与目标的差距

| # | spinfield 流程中的一步 | dingospeed 现状 | 差距 |
|---|---|---|---|
| 1 | 前端提交仓库、文件引用、预期校验值、当前基础版本 | 有单文件上传与批量发布接口 | **无任务提交接口**；**无"当前基础版本"前置条件**（发布不校验父版本） |
| 2 | spinfield 后端校验权限与仓库状态 | 只有共享 token | 无差距——权限归 spinfield，dingospeed 不做（见 §3.2） |
| 3 | 转发参数（含文件位置）给 dingospeed | 字节必须放在 HTTP 请求体里 | 取决于模式选择（§3.1.1）：模式 P **零改动**；模式 R 需新增按路径入库 |
| 4 | 读取文件 | 无 | 无论哪个模式，**用户可控路径 → `open()`** 都是一类全新的攻击面，且必须在 dingospeed 侧也设防 |
| 5 | 在临时目录暂存 | **已有**（暂存 + 原子改名） | 无差距，直接复用 |
| 6 | 校验大小和 Hash | **已有**（收完整体重算 SHA-256） | 无差距，直接复用 |
| 7 | 检查重复内容 | **已有**（`blobReused` 幂等快路径、按摘要寻址天然去重） | 语义需对外暴露给 spinfield，见 SR-6 |
| 8 | 全部文件完成后原子提交新版本 | **已有**（`local-publish` 批量发布） | 需补 baseCommit 前置校验，见 SR-5 |
| 9 | 通知 spinfield 后端任务进度 | 无 | **无出站进度回调**；无任务级进度模型 |
| 10 | 前端实时显示进度 | 无 | spinfield 侧工作，dingospeed 只需保证 9 的质量 |
| 11 | spinfield 更新任务与仓库版本 | 无 | dingospeed 需在终态回调中给出**足以让 spinfield 落库的完整结果**（快照标识、文件数、分类统计） |

### 1.3 目标

1. spinfield 后端能用**一次调用**提交一个"把这批本机文件发布成某仓库某版本"的任务，并拿到任务标识。
2. dingospeed 负责执行全过程：读源文件 → 暂存 → 校验 → 去重 → 全部就绪后原子发布。
3. 任务的进度与终态**主动推送**给 spinfield 后端，且推送可靠、可重放、可对账。
4. 任何中断（进程重启、源文件读失败、校验失败、并发冲突）之后，spinfield 都能**重新提交同一个任务**并得到与一次跑完相同的结果。
5. 用户在 spinfield 前端全程只与 spinfield 后端交互，感知不到 dingospeed 的存在。

### 1.4 一句话价值

> 单文件上传解决"把一个文件安全放到正确位置"，批量发布解决"让一组文件同时出现"。
> 这个增量解决"**让这件事变成平台上一个有主、有权限、有进度、可重试的任务**"。

## 2. 名词与角色

沿用既有文档 §2，新增：

| 名词 | 含义 |
|---|---|
| **入库任务（import task）** | 一次"把 N 个本机文件发布成某仓库某版本"的完整作业。由 spinfield 后端提交，dingospeed 执行 |
| **任务标识（taskId）** | 由 **spinfield 侧生成**并在提交时携带的字符串，同时充当**幂等键**（见 SR-2.3） |
| **源文件（source file）** | dingospeed 所在主机文件系统上的一个已存在文件，是本次入库的字节来源 |
| **源根（source root）** | 配置中允许作为源文件所在位置的目录白名单。任何源路径必须落在其中之一内（见 SR-3） |
| **基础版本（baseCommit）** | 提交任务时调用方声明的"我这次改动是基于哪个快照标识做的"。用于乐观并发控制（见 SR-5） |
| **进度回调（callback）** | dingospeed 主动向 spinfield 后端发起的 HTTP 请求，携带任务状态变化 |

### 2.1 角色职责边界

| 职责 | 归属 | 说明 |
|---|---|---|
| 用户身份、登录态、会话 | **spinfield** | dingospeed 完全不涉及 |
| 仓库归属、成员、读写权限 | **spinfield** | dingospeed 不做任何权限模型（沿用主文档 §3.2） |
| 仓库状态（是否锁定、是否归档、是否允许写） | **spinfield** | dingospeed 只看自己的并发与版本冲突 |
| 任务的业务生命周期、审计、展示 | **spinfield** | dingospeed 的任务对象是执行态，不是业务态 |
| 源文件如何到达服务器本机 | **spinfield** | 浏览器直传、内网拷贝、挂载卷——都与 dingospeed 无关 |
| 源文件的清理 | **spinfield** | **dingospeed 绝不删除、绝不移动、绝不改写源文件**（见 SR-3.4） |
| 字节读取、暂存、校验、去重、发布、原子生效 | **dingospeed** | 本增量的实现主体 |
| 内容落盘形态、清单、快照标识 | **dingospeed** | 沿用既有实现，不得分叉 |
| 防淘汰、残留回收 | **dingospeed** | 沿用既有实现，需覆盖新增残留类别 |

> **为什么要把这张表写死**：两侧各自都可能"顺手把这件事做了"。权限做两遍会漂移，源文件删两遍会丢数据，任务状态存两份会对不上。**每一行只能有一个主。**

## 3. 范围

### 3.1 本期要做

1. **按本机路径入库**的能力：字节来源从 HTTP 请求体扩展为本机文件路径。
2. **入库任务**：提交、查询、取消，以及任务级的进度模型。
3. **出站进度回调**：向 spinfield 后端推送状态变化与终态结果。
4. **基础版本前置校验**：发布时校验当前快照标识是否等于调用方声明的基础版本。
5. **源侧路径安全**：源根白名单与逃逸防护（新的攻击面）。
6. 服务端可选的**源文件摘要预计算**（当 spinfield 无法提供预期摘要时，见 SR-4.2）。
7. 任务残留与新增暂存内容的**回收衔接**。
8. 上述能力的错误分类、日志与交付文档。

### 3.1.1 【硬性约束】字节来源的两种模式，以及它们共同的部署前提

用户的模型文件本来就在 **dingofs**（自研分布式文件系统）上，spinfield 前端提交的是**一个 dingofs 路径**，不是文件内容。这是整个方案的出发点：**前端到后端这一跳不能搬运大文件**。

在此之上，"字节最终怎么进入 dingospeed 的缓存区"有两种模式：

| | **模式 P（推送）** | **模式 R（读取）** |
|---|---|---|
| 谁读 dingofs | spinfield 后端 | dingospeed |
| 跨进程传输 | 回环 HTTP，**全量字节过一遍请求体** | **无** |
| 谁写缓存格式 | dingospeed | dingospeed |
| 总 IO | 1 次读 + 1 次写 + 1 次全量回环往返 | 1 次读 + 1 次写 |
| 断点续传 | 调用方查 `resumeOffset` 后 seek（已实现） | 服务端自己 seek（更简单） |
| **谁把用户给的路径变成 `open()`** | **spinfield 后端** | **dingospeed** |
| dingospeed 侧改动 | **零**（现有接口即可） | 需要新增按路径入库 |

#### 【硬性约束】两种模式的部署前提是同一个

这一点决定了 D-1 怎么答，必须写死：

1. 上传接口**只监听回环地址**（主文档 §4.1，硬性约束，本增量不放宽）。
2. 因此模式 P 中，spinfield 后端**必须与 dingospeed 同机**——否则它连上传接口都调不到。
3. 而模式 P 要求 spinfield 后端能读到 dingofs 路径，即 **dingofs 已挂载在这台主机上**。
4. 于是在同一台主机上，dingospeed 也能读到同一个路径。

**结论：模式 R 的前提被模式 P 的前提完全蕴含。模式 P 可行 ⟹ 模式 R 必然可行；反之不成立。**

在两者都可行时，模式 R 严格更优：少一次全量回环传输、少一次用户态拷贝、断点续传更简单、spinfield 后端不必实现流式上传与续传逻辑。

> **这个推论的价值在于：D-1 不需要在"同机还是分机"上纠结。** 只要坚持回环监听这条硬性约束，同机就是既定事实，剩下的唯一问题是**dingofs 在这台主机上是否已挂载、dingospeed 进程是否有权读**——这是一个可以用一条命令验证的事实，不是一个设计选择。验证方法见【待决 D-1】。

#### 【硬性约束】源路径校验的归属

**谁把用户提交的路径变成 `open()`，谁就必须做源根白名单校验。**

这条与选哪个模式**无关**。模式 P 并不消除风险，只是把它从 dingospeed 挪到 spinfield 后端——而且挪过去更危险：spinfield 后端通常以权限更宽的身份运行，且它读出的内容会直接进入**对外可下载**的缓存区。

**要求**：无论选定哪个模式，**dingospeed 侧的源路径校验都必须实现**（模式 P 下它校验的是 spinfield 已经解析过的路径，属纵深防御）。详见 SR-3。

**【明确不做】**：不做由 dingospeed 主动去远端拉取字节（HTTP/S3/对象存储客户端），不做任何新的外部依赖。

> **为什么**：主文档 §3.2 明确"不引入新的外部依赖，不扩大部署复杂度"。让 dingospeed 具备"去远端拉取任意 URL"的能力，等于给它加一个 SSRF 面和一套重试/超时/鉴权栈，而"文件已经在挂载点上"这个前提让这一切都不必要。

### 3.1.2 【硬性约束】网络边界沿用主文档 §4.1

**任务提交/查询/取消接口与上传、发布接口一样，只允许监听本机回环地址。**

- 与现有上传监听**共用同一个 echo 实例与同一个凭证头**（`X-Dingo-Upload-Token`），不新增对外监听。
- **出站**的进度回调不受此约束（出站是 dingospeed 主动发起的连接），但目标地址必须受配置白名单约束（见 SR-8.4）。

> 这意味着 spinfield 后端必须能访问 dingospeed 的回环地址——与 §3.1.1 的同机/共享存储前提是同一件事的两面。
> 若将来 spinfield 后端必须与 dingospeed 分机部署，那就同时推翻了"读本机文件"这个前提，届时是另一个需求，不是本期放宽监听地址就能解决的。**【待决 D-1】**

### 3.1.3 【硬性约束】允许改什么、不允许改什么

| 层次 | 本增量的要求 |
|---|---|
| 内容落盘（写 blob、暂存与原子改名、摘要重算、块位图、断点续传） | **必须原样复用**，不允许分叉出"路径入库专用"的写入路径 |
| 清单合并、排序、序列化、快照标识计算 | **必须原样复用**（坑 批-4 继续有效），只允许在其之前增加一个基础版本前置判断 |
| 发布的原子性、版本级互斥、仓库级锁 | **必须原样复用** |
| 字节来源 | **本增量的改动点之一**：从 `io.Reader`（请求体）扩展到"打开一个源文件得到的 `io.Reader`" |
| 触发方式与过程可见性 | **本增量的改动点之二**：同步单次调用 → 异步任务 + 进度 |
| 下载侧的任何行为 | **不允许改变** |
| 现有 `local-upload` / `local-upload-progress` / `local-publish` 三个接口的对外行为 | **不允许改变**。spinfield 之外的调用方（脚本、CI）必须继续按原样工作 |

> **判定标准**：把"按路径入库"这条链路的字节来源换回请求体，它应当**退化成现有的 defer 上传 + publish**，且产出的快照标识与现有路径**逐字符相同**。做不到，说明落盘或清单被分叉了。

### 3.2 【明确不做】

| 不做的事 | 原因 |
|---|---|
| 在 dingospeed 侧实现用户体系、RBAC、仓库权限、配额 | 归 spinfield（§2.1）。沿用主文档 §3.2 |
| dingospeed 主动从远端（HTTP/S3/NFS 客户端）拉取字节 | 见 §3.1.1 |
| 一个请求传多个文件的内容（multipart / tar / zip） | 沿用批量增量 §3.1.1。本期连请求体都不用了，更没有理由做 |
| 服务端解压归档、目录递归扫描并自行决定传哪些文件 | 传哪些文件由 spinfield 明确声明。服务端自行遍历会让"清单由调用方声明"这条原则失效，也会让权限判定失去依据 |
| 跨节点调度、集群同步、多副本 | 沿用主文档 §3.1.3，仍仅支持单节点 |
| 从版本中删除文件、整仓替换、回滚已发布版本 | 沿用批量增量。发布仍是合并语义 |
| 任务队列持久化中间件（MQ、数据库、Redis） | 沿用主文档 §3.2，不引入新外部依赖。任务态的可恢复性用"重新提交幂等任务"解决，见 SR-2.3 |
| 双向 RPC、长连接、gRPC 流式推送进度 | 一次 HTTP POST 能表达的事不需要新协议栈。spinfield 前端的实时性由 spinfield 自己的 SSE/WS 提供 |
| 任务优先级、抢占、限速、流量整形 | 沿用主文档 §3.2，无实测瓶颈之前不做 |
| dingospeed 侧的任务历史长期存档与查询 | 业务态归 spinfield。dingospeed 只保留一个短期窗口用于对账，见 SR-7.4 |
| 为本增量新增监控面板或指标体系 | 沿用主文档 FR-8 |

### 3.3 本期不做但需要预留可能性

- **多命名空间 / 组织维度**。**spinfield 当前没有组织模型**，仓库直接映射为 `dingo-local/<repo>`，本期不需要任何映射规则。将来若 spinfield 引入组织（多团队共用仓库），届时才需要决定如何映射——注意当前"本地仓库识别"（坑 1）与"防淘汰"（FR-9）两处判据都是 `org == upload.namespace`，改动它会同时影响这两条数据安全相关的链路，因此**落盘形态不应让将来引入组织变得不可能**（例如不要把仓库名的取值范围用满）。
- **删除已发布版本或其中的文件**。
- **spinfield 侧发起的"预热/分发"联动**（把新发布的版本推到其他节点）。

## 4. 端到端流程

### 4.1 主流程（成功路径）

```text
spinfield 前端                spinfield 后端                    dingospeed
     |                             |                                 |
     |-- 提交发布(仓库/文件/校验值/基础版本) ->|                                 |
     |                             |-- 校验用户权限、仓库状态 --|      |
     |                             |-- 生成 taskId、落库 task ---|     |
     |                             |-- POST /api/local-import/tasks ->|
     |                             |<---- 202 {taskId, accepted} -----|
     |<-- 返回 taskId ------------|                                 |
     |                             |                        [scanning]  逐个 stat 源文件、
     |                             |                                 |  必要时预算 sha256
     |                             |<---- 回调 progress --------------|
     |                             |                     [transferring] 逐个读源文件 →
     |                             |                                 |  暂存 → 重算摘要 →
     |                             |                                 |  原子入 blob（defer）
     |                             |<---- 回调 progress (周期/节流) --|
     |-- 轮询/订阅 spinfield ---->|                                 |
     |<-- 进度 --------------------|                                 |
     |                             |                       [publishing] 校验 baseCommit →
     |                             |                                 |  合并清单 → 原子生效
     |                             |<---- 回调 终态 {commit, 统计} ---|
     |                             |-- 更新任务与仓库版本 -------|      |
     |<-- 完成，展示新版本 -------|                                 |
```

### 4.2 关键失败路径

| 失败点 | dingospeed 行为 | spinfield 行为 |
|---|---|---|
| 源文件不存在 / 不可读 / 路径逃逸 | **提交时同步拒绝**（见 SR-2.2 预检），不创建任务 | 直接把错误回显给用户，不落任务 |
| 某个源文件读到一半失败 | 任务转 `failed`，已暂存内容保留，终态回调列出失败路径 | 展示失败文件；用户修正后重新提交同一 taskId |
| 摘要校验不通过 | 该文件不生效，任务转 `failed`，明确指出是哪个路径 | 同上 |
| baseCommit 与当前不符 | 发布阶段整次拒绝（`PUBLISH_BASE_MISMATCH`），**不产生任何副作用** | 提示"版本已被他人更新"，引导用户以新基础版本重试 |
| dingospeed 进程重启 | 任务丢失，重启后对未知 taskId 的查询返回 `unknown` | 检测到任务长期无进展 → 重新提交同一 taskId（幂等，已完成的文件走快路径） |
| 回调连续失败 | 按 SR-8.3 重试；耗尽后写日志并保留终态供拉取 | 靠定期 `GET /tasks/:taskId` 对账兜底 |

## 5. 接口形态

> 本节约定**形态与检验标准**，具体路径与字段名由实现者定稿，但必须写入交付文档。下列结构是**参考形态**，用于表达必需的信息量。

### 5.1 复杂度检验标准

**一次 N 个文件的入库，spinfield 后端必须能用 1 次调用完成提交，并在此后只被动接收回调。**

- 不允许要求 spinfield 逐个文件调用；
- 不允许要求 spinfield 自己再调一次发布；
- 不允许要求 spinfield 轮询才能拿到终态（轮询只能是对账兜底，不能是主通道）。

超出这个复杂度，说明接口设计跑偏了。

### 5.2 提交任务

```text
POST /api/local-import/tasks
Header: X-Dingo-Upload-Token: <token>
```

```json
{
  "taskId": "spinfield-task-8f3c1a",
  "repoType": "models",
  "org": "dingo-local",
  "repo": "demo",
  "revision": "main",
  "baseCommit": "8c41f9...",
  "overwrite": false,
  "callback": { "url": "http://127.0.0.1:9000/api/dingospeed/import-events" },
  "files": [
    { "path": "config.json",       "sourcePath": "/var/spinfield/staging/8f3c1a/config.json",       "size": 1234,       "sha256": "…" },
    { "path": "sub/model.bin",     "sourcePath": "/var/spinfield/staging/8f3c1a/model.bin",         "size": 3221225472, "sha256": "…" }
  ]
}
```

必需语义：

| 字段 | 要求 |
|---|---|
| `taskId` | 必填，由 spinfield 生成，充当幂等键（SR-2.3） |
| `repoType` / `org` / `repo` / `revision` | 必填，沿用既有校验（含命名空间强制与路径安全矩阵） |
| `baseCommit` | 必填，见 SR-5。空串是合法值，表示"我期望该版本尚不存在" |
| `overwrite` | 作用于整批，语义与 `local-publish` 完全一致 |
| `files[].path` | 仓库内相对路径，沿用既有路径安全校验 |
| `files[].sourcePath` | 本机绝对路径，沿用**新增的源侧安全校验**（SR-3） |
| `files[].size` | 必填。与 `stat` 结果不符即拒绝 |
| `files[].sha256` | 可选，见 SR-4.2。提供时既是绑定值也是预期值；缺省时由服务端预计算 |
| `callback.url` | 可选。缺省时使用配置中的默认回调地址；无论哪种都必须通过白名单校验（SR-8.4） |

响应：`202` + `{ "taskId": "...", "state": "accepted", "totalFiles": 2, "totalBytes": 3221226706 }`。

### 5.3 查询任务

```text
GET /api/local-import/tasks/:taskId
```

返回与回调载荷**同构**的任务快照（见 SR-7）。这是对账通道，不是主通道。

### 5.4 取消任务

```text
POST /api/local-import/tasks/:taskId/cancel
```

语义见 SR-9。

### 5.5 进度回调（dingospeed → spinfield）

```text
POST <callback.url>
Header: X-Dingo-Event-Signature: <HMAC-SHA256(body, secret)>
Header: X-Dingo-Event-Id: <幂等键>
```

载荷即任务快照（SR-7），spinfield 侧必须按 `seq` 去重与排序。

## 6. 功能需求

### SR-1 按路径入库 【硬性约束 —— 仅模式 R 需要】

> **适用范围**：本节仅在选定**模式 R**（dingospeed 自己读挂载点）时需要实现。
> 选定**模式 P**（spinfield 后端读、经请求体推送）时，本节整节**不做**——现有 defer 上传接口已经满足，spinfield 后端按既有的"查 `resumeOffset` + 带 `start` 续传"方式调用即可。
>
> **其余所有章节（SR-2 ~ SR-12）与模式选择无关，两种模式下都要做。** 这是本文档刻意的结构：把可能变的那部分收敛到一节里。

#### 6.1.1 字节来源的唯一变化点

按路径入库与现有 defer 上传的**唯一区别**是：字节来自 `open(sourcePath)` 而不是 HTTP 请求体。

在此之下的一切**必须完全一致**：

| 项 | 要求 |
|---|---|
| 暂存位置与原子改名 | 与现有一致 |
| 摘要校验 | 内容完整后**整个读一遍重算**，不做流式累加（主文档 §3.3.1 第 1 条继续有效） |
| 写入方式 | 复用按块写入，不得改成只能追加（主文档 §3.3.1 第 2 条继续有效） |
| 块位图与可续传偏移 | 与现有一致，仍从缓存文件形态推导 |
| 内存占用 | 与文件大小无关。**不得把源文件整个读进内存或 mmap 整个文件** |
| 同文件互斥、blob 级互斥、版本级互斥 | 与现有一致 |
| 幂等快路径 | 与现有一致，需在任务结果中体现为 `reused` |

**【明确不做】**：不要为路径入库新写一份落盘逻辑；不要因为"源在本机、可以随机读"就发明一条新的写入路径。

#### 6.1.2 【硬性约束】不得用文件系统层的快捷方式代替内容写入

**不允许**用 `rename`、`link`、`reflink`、`copy_file_range` 直接把源文件变成 blob。

> **为什么**：主文档坑 2——缓存文件不是原始文件的副本，它是带头部与块位图的自定义格式。把源文件原样挪过去，下载侧读到的就是乱的。
> 这条要单独写出来，是因为"源文件就在本机"这个新前提，会让"直接 link 过去多快啊"成为一个**极其自然但完全错误**的念头。

#### 6.1.3 续传语义的简化

源文件在本机且可随机读，因此中断恢复不再需要调用方参与：**服务端自己从块位图取可续传偏移，`seek` 到该位置继续读**。

- 这不改变可续传偏移的定义（主文档 FR-4.2），只是把"谁来 seek"从调用方换成了服务端。
- **【明确不做】**：不要因此引入新的进度存储（主文档 FR-4.5 继续有效）。偏移仍然只有一个来源——缓存文件本身。

### SR-2 入库任务的生命周期

#### 6.2.1 任务状态机

```text
accepted → scanning → transferring → publishing → succeeded
    ↓          ↓            ↓             ↓
  failed <---+------------+-------------+
    ↑
 canceled（仅可从 scanning / transferring 进入，见 SR-9）
```

| 状态 | 含义 |
|---|---|
| `accepted` | 已通过提交时预检，等待执行 |
| `scanning` | 正在 stat 源文件、必要时预计算摘要 |
| `transferring` | 正在逐个读取源文件并落盘（defer 语义，下载方看不到任何变化） |
| `publishing` | 全部内容就绪，正在校验 baseCommit 并原子发布 |
| `succeeded` | 发布完成，`commit` 已产生 |
| `failed` | 任意阶段失败，携带失败分类与失败路径 |
| `canceled` | 被显式取消 |

#### 6.2.2 提交时同步预检 【硬性约束】

以下检查必须在**返回 202 之前**完成，不通过则**不创建任务**，同步返回错误：

| 检查项 | 失败码 |
|---|---|
| 凭证 | 沿用 `UPLOAD_*` 三类 |
| `taskId` 缺失或非法 | `IMPORT_INVALID_ARGUMENT` |
| 仓库定位四字段（含命名空间与路径安全） | `IMPORT_INVALID_ARGUMENT` |
| 清单为空 / 超上限 / 含重复仓库内路径 | `IMPORT_INVALID_ARGUMENT` |
| 清单中 `sourcePath` 重复指向同一源文件但声明了不同仓库内路径 | **允许**（一份内容发布到两个路径是合法的） |
| 源路径逃逸源根、不存在、不是普通文件、不可读 | `IMPORT_SOURCE_UNAVAILABLE`，**列出具体路径** |
| `stat` 出的大小与声明不符 | `IMPORT_SOURCE_SIZE_MISMATCH`，列出路径 |
| 目标磁盘可用空间不足以容纳本批次总字节 | `IMPORT_INSUFFICIENT_SPACE` |
| 回调地址不在白名单内 | `IMPORT_CALLBACK_REJECTED` |

> **为什么预检要做在同步返回之前**：这些错误 100% 是调用方的参数问题，能立刻答出来。让它们走异步回调，等于逼 spinfield 为"路径打错一个字"也建一个任务、也走一遍回调、也在前端展示一个失败任务。**能同步告知的错误不要异步化。**

#### 6.2.3 幂等 【硬性约束】

**同一个 `taskId` 重复提交，必须是幂等的。**

| 当前任务状态 | 重复提交时的行为 |
|---|---|
| 不存在 | 正常创建 |
| `accepted` / `scanning` / `transferring` / `publishing` | 返回当前任务快照，**不新建、不重启**，响应中标明"已存在" |
| `succeeded` | 返回原终态快照（含原 `commit`），不重新执行 |
| `failed` / `canceled` | **重新执行**。已完整落盘的文件走幂等快路径直接跳过，未完成的从块位图续传 |
| 存在但请求体与原任务的仓库定位或清单**不一致** | 拒绝，`IMPORT_TASK_CONFLICT`，明确告知 taskId 已被占用 |

> **为什么幂等键由 spinfield 生成而不是 dingospeed 返回**：dingospeed 的任务态是易失的（见 SR-7.3）。如果标识由 dingospeed 生成，那么"提交成功但 spinfield 没收到响应"这一种情况，spinfield 就永远无法把重试关联到原任务上，只能盲目新建，产生重复执行。让调用方带 ID 进来，这个问题结构上就不存在。

### SR-3 源侧路径安全 【硬性约束 —— 本增量最重要的安全需求】

> **这是一个全新的攻击面。** 既有的路径安全矩阵全部是**目标侧**的——保证"字节写到哪"不逃逸缓存根。本增量第一次引入**源侧**输入："从哪读字节"，而且这个输入**由前端用户提供**。
>
> 一个不设防的实现，等于把一个**任意文件读取**原语接到了对外的下载端口上：把路径指向 `/etc/shadow`、私钥或其他用户的数据目录，内容入库成一个"模型文件"，然后从下载侧公开读出来。**这比目标侧逃逸更严重**——目标侧逃逸是写坏系统，源侧逃逸是泄露系统。
>
> **【硬性约束】本节要求与 §3.1.1 的模式选择无关。** 模式 P 不消除这个风险，只是把执行点挪到 spinfield 后端。因此：
>
> | 模式 | spinfield 后端 | dingospeed |
> |---|---|---|
> | R | 建议同样校验（早失败、错误信息更贴近用户） | **必须实现本节全部要求** |
> | P | **必须实现本节等价的校验**（它才是真正执行 `open()` 的一方） | **仍必须实现本节要求**，对象是 spinfield 声明的路径——纵深防御，不得因"上游校验过了"而省略 |
>
> 两侧都做的成本很低（一次 `realpath` + 前缀比对），而任何一侧漏掉的代价是全系统级的信息泄露。

#### 6.3.1 源根白名单

- 新增配置 `upload.import.sourceRoots`（列表）。**为空则按路径入库能力整体关闭**（与 `upload.token` 为空则上传关闭同一原则：默认关闭，不是默认放行）。
- 每个源根在服务启动时解析为**绝对且已解析符号链接**的真实路径。
- 任何 `sourcePath` 必须满足：解析符号链接后的真实路径，**是某个源根的真子路径**。

#### 6.3.2 必须拒绝的形式

| 形式 | 处理 |
|---|---|
| 相对路径、`..` 及其各种编码变形 | 拒绝 |
| 指向源根之外的符号链接（**含路径中间环节的符号链接**） | 拒绝 |
| 硬链接指向源根之外的 inode | 见下方说明 |
| 非普通文件（目录、设备、FIFO、socket） | 拒绝 |
| NUL 及控制字符 | 拒绝 |
| Windows 盘符/UNC 前缀出现在非预期字段 | 拒绝 |

> **关于硬链接**：符号链接可以在打开前解析并判定，硬链接不能——它没有"指向哪"这个信息。因此**不要试图在校验阶段检测硬链接**，那是做不到的。正确的防线是**运维层面**：源根必须是一个只有 spinfield 写入的专用目录，且**不与系统敏感目录同属一个文件系统**（否则用户可以在源根内 `ln` 一个敏感文件进来）。这一条必须写入交付文档的部署要求，并作为【待决 D-2】与运维确认。

#### 6.3.3 TOCTOU 防护 【硬性约束】

路径校验与真正打开文件之间存在时间窗，源文件可能在这期间被替换成一个符号链接。

**要求**：以"**先打开、后校验已打开的这个 fd**"的顺序进行，而不是"先校验路径字符串、后打开"。校验对象必须是**已打开的文件描述符本身**（其真实路径、类型、大小），不能是校验时的那个字符串。

#### 6.3.4 源文件只读 【硬性约束】

**dingospeed 对源文件只做打开、读取、关闭三件事。**

**【明确不做】**：不删除、不移动、不重命名、不截断、不改权限、不改时间戳。任务成功之后也不做。源文件的清理是 spinfield 的责任（§2.1）。

> **为什么写死**："入库成功后顺手把源文件删了以省磁盘"是一个非常自然的想法，而且第一次一定是对的。但只要出现"同一个源文件被两个任务引用"或者"spinfield 还要用它做别的事"，它就是不可恢复的数据丢失。**释放空间由持有者做，执行者不做。**

#### 6.3.5 读取期间源文件被修改

源文件在读取期间可能被外部改动（截断、追加、原地覆写）。

**要求**：不需要防止这件事发生，但必须**检测得出来**——最终的整体摘要重算会兜住内容变化；同时读取过程中实际读到的字节数与声明大小不符时必须拒绝。

**【明确不做】**：不做文件锁、不做写时复制快照。检测得出、拒绝得掉即可。

### SR-4 校验值语义

#### 6.4.1 双重校验 【硬性约束】

spinfield 声明的 `size` 与 `sha256` 是**预期值**，服务端的重算结果是**权威值**。二者不符，该文件不生效，任务失败。

沿用主文档坑 4：**标识必须由服务端依据实际落盘内容计算**，调用方的声明只用于绑定与比对。

#### 6.4.2 摘要缺省时的服务端预计算

spinfield 前端未必总能拿到 SHA-256——浏览器对大文件算摘要成本高，而文件可能是通过别的通道落到服务器上的。

**要求**：`sha256` 允许缺省。缺省时进入 `scanning` 阶段，由服务端**完整读一遍源文件**算出摘要，再进入落盘阶段。

| 项 | 要求 |
|---|---|
| 与 FR-2 的关系 | **不违反**。FR-2 要求的是"写第一个字节之前服务端必须已知摘要"，预计算恰好满足 |
| 代价 | 源文件被读两遍。必须在进度模型中体现为独立阶段，让用户看得到 |
| 开关 | 配置 `upload.import.allowServerSideHash`，默认开启。关闭时缺省摘要直接拒绝 |
| spinfield 提供了摘要时 | **不做预计算**，直接进入落盘，仍以落盘后重算为准 |

> **不要把预计算的结果当成"用户声明的值"记账**。它是服务端自己算的，两者在审计意义上不同：前者能证明"内容与提交者的意图一致"，后者不能。终态回调中应能区分某个文件的摘要是**声明的**还是**服务端补算的**。

### SR-5 基础版本前置校验 【硬性约束 —— 新增语义】

#### 6.5.1 语义

发布阶段，在合并清单**之前**，校验该 `repoType/org/repo/revision` 当前指向的快照标识是否等于提交时声明的 `baseCommit`：

| 情况 | 行为 |
|---|---|
| 相等 | 正常发布 |
| 声明为空串，且该 revision 当前**不存在** | 正常发布（首次创建） |
| 声明为空串，但该 revision **已存在** | 拒绝，`PUBLISH_BASE_MISMATCH`，返回**当前实际的** commit |
| 不相等 | 拒绝，`PUBLISH_BASE_MISMATCH`，返回当前实际的 commit |

拒绝时**不产生任何副作用**：不改清单、不改版本标签、不写任何元数据。已暂存的内容保留（等待 spinfield 以新基础版本重新提交）。

#### 6.5.2 与空变更的关系

若 baseCommit 校验通过、但合并后清单与当前完全相同（批量增量 BR-2.3 的空变更），仍按原语义处理：成功返回、快照标识不变、不重写元数据。任务终态为 `succeeded`，并标明 `changed: false`。

#### 6.5.3 校验必须与发布在同一把锁内 【硬性约束】

**"读当前 commit → 比对 baseCommit → 合并清单 → 原子生效"必须整体处于既有的版本级互斥之内。**

> **为什么**：否则这是一个教科书式的 TOCTOU——A 校验通过、还没写，B 完成了一次发布，A 接着基于陈旧清单写下去，B 的改动被静默吞掉。这正是主文档坑 8 与批量增量坑 批-7 的形态，只是这次多了一个"看起来已经防住了"的错觉。

#### 6.5.4 对既有接口的影响

- `local-publish` 接口**新增可选**参数表达 baseCommit。**不传时行为与现在逐字节一致**（沿用批量增量 §3.1.2 的兼容原则）。
- 路径入库任务的 `baseCommit` 是**必填**——spinfield 一定持有它，没有理由省略。

### SR-6 重复内容的识别与反馈

内容按摘要寻址，去重能力已经存在。本增量的要求是**把它对 spinfield 说清楚**。

任务终态中每个文件必须落入且仅落入以下一类：

| 分类 | 含义 |
|---|---|
| `written` | 内容此前不在盘上，本次实际写入 |
| `reused` | 相同摘要的内容已在盘上，未重复写入（对应 `blobReused`） |
| `unchanged` | 该仓库内路径已生效且摘要相同，本次发布对它无变化 |
| `replaced` | 该仓库内路径已生效但摘要不同，本次按 `overwrite` 覆盖 |
| `failed` | 失败，附失败原因与分类 |
| `skipped` | 任务被取消时未开始处理的文件 |

**【明确不做】**：不做跨仓库的全局内容索引，不做去重统计报表（沿用主文档 FR-2.5）。

---

### SR-7 任务进度模型

#### 6.7.1 进度必须是字节级的，且来源唯一 【硬性约束】

| 指标 | 定义 |
|---|---|
| `totalFiles` / `totalBytes` | 清单声明值，任务创建后不变 |
| `doneFiles` | 已进入 `written` / `reused` / `unchanged` 的文件数 |
| `doneBytes` | **已持久化的**字节数：已完成文件的完整大小 + 当前文件的**可续传偏移**（沿用主文档 FR-4.2 的定义） |
| `currentFile` | 当前处理的仓库内路径与其阶段 |
| `phase` | 见 SR-2.1 状态机 |
| `seq` | 单调递增的事件序号，用于回调去重与排序 |

> **`doneBytes` 绝不能用"已从源文件读了多少字节"**。那正是主文档坑 11 在进度展示上的变体：用户会看到进度回退（重启后回到上一个块边界），如果用读取字节数，回退幅度和真实持久化位置对不上，"继续传"之后的进度会跳跃或倒退得莫名其妙。**从块位图推导，进度就总是可解释的。**

#### 6.7.2 进度必须单调，回退必须可解释

同一任务同一次执行内，`doneBytes` 必须单调不减。任务重新执行（幂等重提交）时允许从更低的值开始，此时 `attempt` 计数必须递增，让 spinfield 能区分"回退"与"乱序回调"。

#### 6.7.3 任务态是易失的，内容态是权威的 【硬性约束】

**dingospeed 侧的任务对象允许只存在于内存中，进程重启即丢失。**

| 数据 | 权威来源 |
|---|---|
| 内容是否完整落盘、可续传偏移 | **磁盘**（块位图），进程重启后完全可恢复 |
| 某版本当前的清单与快照标识 | **磁盘**（清单与版本元数据） |
| 任务的进度、阶段、失败原因 | **内存**，重启后丢失 |

重启后对未知 taskId 的查询返回 `unknown`（HTTP 404 + `IMPORT_TASK_UNKNOWN`），spinfield 据此重新提交同一任务。

> **为什么允许丢**：这是主文档 FR-4.5 与批量增量 BR-1.3 的同一条原则的第三次应用——**独立状态与实际落盘内容之间必然出现不一致**。任务进度是派生数据，重建的代价是"重新提交一次，已完成的走快路径"，几乎为零；而持久化它换来的是一整套"状态文件与磁盘对不上"的排查地狱。
>
> **对 spinfield 的要求**：spinfield 必须把 `unknown` 当作**正常情况**处理（重新提交），不能当作错误告警。这一条要写进对接文档。

#### 6.7.4 终态保留窗口

`succeeded` / `failed` / `canceled` 的任务快照在内存中保留一个可配置的窗口（`upload.import.taskRetentionHours`，默认 24），供 spinfield 对账。超期后按 `unknown` 处理。

**【明确不做】**：不做任务历史持久化、不做任务列表查询接口、不做按仓库检索任务。业务态归 spinfield。

### SR-8 进度回调

#### 6.8.1 触发时机

| 事件 | 时机 |
|---|---|
| 阶段变化 | 每次 `phase` 变化立即回调 |
| 文件完成 | 每个文件进入终态时回调（可与周期回调合并） |
| 周期进度 | 每 `upload.import.progressIntervalSeconds`（默认 3 秒）一次，**无变化时不发** |
| 终态 | `succeeded` / `failed` / `canceled` 时**必须**回调 |

> **节流是必需的**：一个 1000 文件的任务，如果每个块都回调一次，spinfield 会被打爆。周期 + 变化点的组合足够了。

#### 6.8.2 终态回调的信息完整性 【硬性约束】

终态回调必须携带**足以让 spinfield 直接落库并更新仓库版本的全部信息**，不允许要求 spinfield 再发一次查询：

- 任务标识、终态、`attempt`；
- 成功时：`commit`、`changed`、`fileCount`（合并后总数）、`published`、`added` / `replaced` / `unchanged` 统计；
- 失败时：失败分类、失败的仓库内路径列表及各自原因；
- 每个文件的最终分类（SR-6）。

#### 6.8.3 投递保证

| 项 | 要求 |
|---|---|
| 语义 | **至少一次**。允许重复，不允许静默丢失终态 |
| 去重 | 每次回调携带唯一 `eventId` 与单调 `seq`，由 spinfield 去重 |
| 重试 | 失败按指数退避重试，次数与超时可配（`callbackMaxRetries` 默认 5，`callbackTimeoutSeconds` 默认 5） |
| 耗尽后 | 写 ERROR 日志，任务终态仍完整保留在查询接口上（SR-7.4），由 spinfield 对账兜底 |
| 顺序 | 不保证到达顺序。**spinfield 必须按 `seq` 处理，丢弃比已处理值小的事件** |
| 非终态事件 | 允许丢弃（周期进度失败不重试，下一个周期会带上更新的值） |

> **不要为了"保证顺序"引入队列或串行化**。让接收方按序号取最大值，是成本最低且最健壮的做法。

#### 6.8.4 回调目标的安全约束 【硬性约束】

出站回调是 dingospeed 第一次向"调用方指定的地址"发起请求，这是 SSRF 面。

| 要求 | 说明 |
|---|---|
| 白名单 | `upload.import.callbackAllowedHosts` 配置允许的 host（含端口）。不在白名单内一律拒绝，**在提交时同步拒绝** |
| 默认值 | 建议默认只允许回环地址，与 §3.1.1 的同机部署前提一致 |
| 协议 | 只允许 http/https，拒绝其他 scheme |
| 重定向 | **不跟随重定向** |
| 签名 | 请求体用共享密钥做 HMAC-SHA256，放在请求头。密钥配置项 `upload.import.callbackSecret` |
| 载荷 | **不得包含源文件绝对路径以外的任何主机信息**；不得包含 token、配置内容或目录列表 |

### SR-9 取消

| 项 | 要求 |
|---|---|
| 可取消的状态 | `accepted` / `scanning` / `transferring` |
| **不可**取消的状态 | `publishing`。发布是原子的，**中途取消没有意义且会引入中间态**，此时取消请求应被明确拒绝并告知"发布已开始" |
| 取消后的内容 | 已暂存的内容**保留**（可能被后续重试复用），由 orphan 回收机制按期清理 |
| 取消后的版本 | 版本标签与快照标识**保持原样**，不产生任何新元数据 |
| 幂等 | 重复取消返回相同结果 |
| 回调 | 必须发出 `canceled` 终态回调 |

---

### SR-10 并发与资源

| 项 | 要求 |
|---|---|
| 任务级并发 | 同时执行的入库任务数有上限（`upload.import.maxConcurrentTasks`，建议默认 2），超出排队或明确拒绝——**二选一，需在交付文档写明** |
| 文件级并发 | 一个任务内同时处理的文件数受既有 `upload.concurrentLimit` 约束。**不得绕过它**——它保护的是磁盘 IO，不是 HTTP 连接数 |
| 同一 revision 的多任务 | 允许并存于 `transferring`（暂存互不影响），但 `publishing` 受既有版本级互斥串行化，且第二个会因 baseCommit 不符而失败——**这是正确行为**，不要为它做等待或自动重试 |
| 与既有 HTTP 上传的关系 | 共享同一套并发额度与互斥。路径入库不得比 HTTP 上传拥有更高优先级 |
| 磁盘空间 | 提交时预检总字节数，执行中空间不足必须**明确失败**而不是写坏 |

---

### SR-11 残留与回收

本增量不引入新的残留**类别**——路径入库产生的暂存内容与 defer 上传完全同类，由既有的 `stagingRetentionHours` / `orphanRetentionHours` 机制覆盖。

**要求**：

1. 确认失败/取消的任务留下的暂存内容与待发布内容**确实落入既有回收范围**，并有用例证明。
2. 回收的误删防护继续有效（批量增量 BR-6.2 第 3 条）：引用判定必须扫遍该仓库全部快照清单。
3. 内存中的任务对象超过保留窗口后释放，**任务数不得无限增长**。

---

### SR-12 可观测性与错误分类

#### 6.12.1 日志

任务的创建、每个阶段变化、每个文件的终态分类、每次回调的成败、每次拒绝的原因都要有日志，且都带 `taskId`。

**源路径逃逸、回调目标被拒、凭证失败**这三类安全事件必须能在日志中被单独识别出来。

#### 6.12.2 新增错误码

| 错误码 | HTTP | 含义 |
|---|---:|---|
| `IMPORT_DISABLED` | 403 | 未配置源根，路径入库能力关闭 |
| `IMPORT_INVALID_ARGUMENT` | 400 | taskId / 定位字段 / 清单形状非法 |
| `IMPORT_SOURCE_UNAVAILABLE` | 400 | 源路径逃逸、不存在、非普通文件、不可读（列出路径） |
| `IMPORT_SOURCE_SIZE_MISMATCH` | 400 | 源文件实际大小与声明不符（列出路径） |
| `IMPORT_SOURCE_CHANGED` | 409 | 读取期间源文件发生变化 |
| `IMPORT_INSUFFICIENT_SPACE` | 507 | 目标磁盘可用空间不足 |
| `IMPORT_CALLBACK_REJECTED` | 400 | 回调地址不在白名单内 |
| `IMPORT_TASK_CONFLICT` | 409 | taskId 已存在但请求内容不一致 |
| `IMPORT_TASK_UNKNOWN` | 404 | 任务不存在或已超出保留窗口 |
| `IMPORT_TASK_NOT_CANCELABLE` | 409 | 任务已进入 publishing 或已是终态 |
| `IMPORT_TASK_LIMIT` | 429 | 超过并发任务上限 |
| `PUBLISH_BASE_MISMATCH` | 409 | 基础版本与当前快照标识不符，响应中返回当前实际值 |

既有 `UPLOAD_*` / `PUBLISH_*` 错误码在任务失败详情中**原样透传**，不重新编码。

> **为什么要透传而不是包一层**：spinfield 需要向用户解释"为什么失败"。把 `UPLOAD_OVERWRITE_REQUIRED` 包装成 `IMPORT_FAILED` 会丢掉唯一有用的信息。

## 7. 已知风险与踩坑点

### 坑 接-1：源路径成了任意文件读取原语 🔴

**是什么**
持有上传 token 的一方（或任何能影响 spinfield 提交参数的路径）把 `sourcePath` 指向 `/etc/shadow`、私钥、其他用户的数据目录，内容被入库成一个模型文件，然后从**对外的下载端口**公开读出来。

**怎么来的**
既有的路径安全校验全部是目标侧的，天然不覆盖"从哪读"。而"按路径读文件"这个能力一旦加上，它的默认状态就是**能读进程有权限读的一切**。

**特别提醒：这个风险不会因为"换一侧来读"而消失。** 把读取动作放在 spinfield 后端（模式 P），只是把同一个漏洞挪进 spinfield，而且挪过去往往更危险——后端进程的身份通常更宽，且读出的内容照样进入对外可下载的缓存区。**风险跟着"谁执行 `open()`"走，不跟着"谁叫 dingospeed"走。**

**解决方向**
见 SR-3：源根白名单 + 默认关闭 + 打开后校验 fd（防 TOCTOU）+ 源根与敏感目录不同文件系统。**两侧都做**，dingospeed 侧那份是纵深防御，不得省略。

**验收**：源侧逃逸矩阵必须**独立跑一遍**，不能因为"目标侧已经校验过"就跳过。用例必须包含：中间环节符号链接、软链接指向源根外、`..` 变形、非普通文件、校验通过后立刻替换成软链接（TOCTOU）。

---

### 坑 接-2：顺手把源文件 link 或 rename 成 blob 🔴

**是什么**
下载报错或内容乱码。

**怎么来的**
"源文件就在本机，何必再拷一遍"是一个极其自然的优化念头。但缓存文件不是原始文件的副本（主文档坑 2）。

**解决方向**
见 SR-1.2：内容必须走既有的按块写入路径。**"源在本机"只改变字节从哪读，不改变字节怎么写。**

---

### 坑 接-3：进度用了"读了多少字节" 🔴

**是什么**
用户看着进度条走到 60%，服务重启后回到 45%，续跑之后又莫名跳到 62%。或者进度显示 100% 但任务还在跑。

**怎么来的**
主文档坑 11 在展示层的重演。读取字节数与持久化偏移在中断时不相等。

**解决方向**
见 SR-7.1：`doneBytes` 从块位图推导。回退是正常的，但必须是**可解释的**回退（回到块边界）。

---

### 坑 接-4：baseCommit 校验做在了锁外 🔴

**是什么**
两个用户几乎同时发布，都通过了 baseCommit 校验，后写的把先写的静默覆盖掉。基础版本校验**看起来做了**，但完全没起作用。

**怎么来的**
"先查一下当前版本、对得上再走原来的发布流程"是最省事的接法，而它恰好把校验和写入拆成了两个临界区。

**解决方向**
见 SR-5.3：校验与发布必须在同一把版本级锁内。

**验收**：专门构造两个任务对同一 revision 声明相同 baseCommit 并发发布的用例，验证**恰好一个成功、另一个明确失败**，且失败方不产生任何副作用。

---

### 坑 接-5：把任务状态持久化了 🔴

**是什么**
系统跑一段时间后出现"任务状态文件说传完了，磁盘上没有内容"或者相反的破损状态，且极难排查。

**怎么来的**
"任务重启就丢了，用户体验不好，存一下吧"是一个善意且致命的念头。它把主文档 FR-4.5 明令禁止的东西换了个名字加了回来——进程一定会崩在"写完数据"和"更新状态"之间。

**解决方向**
见 SR-7.3：任务态易失，内容态权威，重启后靠幂等重提交恢复。**如果确实需要任务历史，那份历史属于 spinfield，不属于 dingospeed。**

---

### 坑 接-6：终态回调丢了，两边状态永久分歧

**是什么**
dingospeed 认为任务成功、版本已发布；spinfield 的任务永远停在"进行中"，用户看到一个转不完的圈。

**怎么来的**
回调是网络调用，一定会失败。只做"发一次，失败就算了"必然出现分歧。

**解决方向**
见 SR-8.3：终态至少一次 + 重试 + 保留窗口内可查询 + spinfield 侧定期对账。**三层里任何一层单独都不够。**

**验收**：构造"回调目标全程不可达"的用例，验证任务本身正常完成、终态可通过查询接口取到、日志中有明确记录。

---

### 坑 接-7：预检不做，全部错误异步化

**是什么**
用户把路径打错一个字，前端要等 10 秒才看到一个失败任务，而且任务列表里堆满了从没真正开始过的失败记录。

**怎么来的**
"统一走异步，实现简单"。

**解决方向**
见 SR-2.2：能同步判定的错误必须同步返回，且不创建任务。

---

### 坑 接-8：spinfield 太早删源文件

**是什么**
任务失败重试时源文件已经不在了，只能让用户重新上传一遍几十 GB 的权重。

**怎么来的**
spinfield 收到"某个文件已完成"的进度事件就认为可以清理了。但任务可能在后续文件上失败，重试需要**整批**源文件仍然在位。

**解决方向**
写入对接文档：**spinfield 只能在收到任务终态 `succeeded` 之后清理源文件**；`failed` 时必须保留至少一个可配置的窗口，供用户重试。dingospeed 侧无法防止这件事，只能靠约定——因此它必须被明确写出来。

---

### 坑 接-9：把 dingofs 当成普通本地盘来做安全校验 🔴

**是什么**
源路径校验在本地 ext4 上测试全过，接到真实的 dingofs 挂载点上却失效：`realpath` 结果不符合预期、软链接语义与本地盘不同、或者用于 TOCTOU 防护的"打开后回查 fd 真实路径"在这个文件系统上根本拿不到可靠答案。

**怎么来的**
dingofs 是自研的分布式文件系统（GPFS 类）。SR-3 的两条核心防线——**符号链接解析**与**先开后验 fd**——都依赖具体文件系统与 VFS 的行为细节。若挂载走 FUSE，`/proc/self/fd/N` 的 readlink 结果、`O_NOFOLLOW` 的语义、`stat` 的一致性窗口都可能与本地盘不同。**在本地盘上测过不代表在 dingofs 上成立。**

另有三个与本地盘不同、会直接影响正确性的行为需要实测确认：

| 行为 | 为什么重要 |
|---|---|
| 写入方写完之前，读取方是否可能看到**部分内容** | 关系到 SR-3.5"读取期间源文件被修改"的检测是否够用 |
| `stat` 出的大小与实际可读字节数是否**始终一致** | 关系到提交时预检（SR-2.2）能否信任 |
| 挂载点是**每节点独立**还是**全局共享同一份** | 关系到主文档 §3.1.3 单节点约束的表述是否需要修订 |

**解决方向**
**源侧安全的验收（§9.2）必须在真实 dingofs 挂载点上跑一遍**，不能只在本地盘上跑。若某条防线在 dingofs 上不成立，必须**先找到等价替代再动工**，不允许降级为"大概没问题"。

**验收**：§9.2 全表在真实挂载点上重跑，并记录 dingofs 的实测行为差异。

---

## 8. 非功能需求

| 项 | 要求 |
|---|---|
| **性能** | 单文件入库吞吐不应显著低于"源盘顺序读 + 目标盘顺序写"的下限。缺省摘要触发的预计算会使源文件被读两遍，这是已知代价，需在文档中说明 |
| **内存** | 沿用主文档：与被入库文件大小无关。任务对象的内存占用与清单条目数线性相关，与文件内容无关 |
| **稳定性** | 任务的任何异常中断，都不得损坏已生效数据；不得损坏该版本中其他已生效文件 |
| **兼容性** | 现有 `local-upload` / `local-upload-progress` / `local-publish` 三个接口不带新参数时行为**逐字节不变**；下载侧行为不变；ModelScope 通道不受影响 |
| **部署** | 仍仅支持单节点；不引入任何新的外部依赖组件 |
| **安全** | 新增的源侧输入必须达到与既有目标侧路径安全**同等**的严格程度（§7 坑 接-1） |
| **新增配置项** | `upload.import.sourceRoots`、`upload.import.maxConcurrentTasks`、`upload.import.maxFilesPerTask`、`upload.import.allowServerSideHash`、`upload.import.taskRetentionHours`、`upload.import.progressIntervalSeconds`、`upload.import.callbackAllowedHosts`、`upload.import.callbackSecret`、`upload.import.callbackTimeoutSeconds`、`upload.import.callbackMaxRetries`。实现者需在交付文档中完整列出并说明与既有 `upload.*` 的关系 |
| **可维护性** | 路径入库与 HTTP 上传**共用同一套落盘、清单、标识实现**，不允许复制一份改改用（沿用批量增量坑 批-4 的原则） |

### 9.1 等价性（核心验收，仅模式 R）🔴

### 9.2 源侧安全（针对坑 接-1、坑 接-9，必测）

> **本表必须在真实的 dingofs 挂载点上跑一遍**，本地盘上通过不构成验收（坑 接-9）。

| 用例 | 期望 |
|---|---|
| 未配置源根时提交任务 | 拒绝，`IMPORT_DISABLED` |
| `sourcePath` 为相对路径 / 含 `..` / 各种编码变形 | 全部拒绝 |
| `sourcePath` 最终环节是指向源根外的软链接 | 拒绝 |
| **路径中间环节**是指向源根外的软链接 | 拒绝 |
| `sourcePath` 指向目录 / 设备 / FIFO | 拒绝 |
| 校验通过后、打开前把文件替换为软链接（TOCTOU） | 拒绝或读到的仍是原文件，**绝不读到源根外内容** |

### 9.3 基础版本（针对坑 接-4）

| 用例 | 期望 |
|---|---|
| baseCommit 等于当前 | 发布成功 |
| baseCommit 为空且 revision 不存在 | 发布成功 |
| baseCommit 为空但 revision 已存在 | 拒绝，返回当前 commit |
| baseCommit 为陈旧值 | 拒绝，返回当前 commit，**版本标签与元数据保持原样** |
| 两个任务声明相同 baseCommit 并发发布 | **恰好一个成功**，另一个明确失败且无副作用 |
| `local-publish` 不带 baseCommit | 行为与本增量之前**逐字节一致** |

### 9.4 任务生命周期与幂等（针对 SR-2.3、坑 接-5）

| 用例 | 期望 |
|---|---|
| 同一 taskId 在进行中重复提交 | 返回当前快照，不新建、不重启 |
| 同一 taskId 在 succeeded 后重复提交 | 返回原终态与原 commit，不重新执行 |
| 同一 taskId 在 failed 后重复提交 | 重新执行，已完成文件走快路径，未完成的续传，最终结果与一次跑完**逐字节一致** |
| 同一 taskId 但清单不同 | 拒绝，`IMPORT_TASK_CONFLICT` |
| 传输中途杀掉进程，重启后查询 | 返回 `unknown`；重新提交后正确续跑 |
| 中断 3 次以上再跑完 | 结果与一次跑完一致 |

### 9.5 进度正确性（针对坑 接-3）

- 大文件入库过程中采样进度，验证 `doneBytes` **单调不减**，且始终**不大于**实际持久化字节数。
- 中断后重新提交，验证进度回退到**块边界**，且 `attempt` 递增。
- 缺省摘要的任务，验证 `scanning` 阶段可见、进度可解释、不出现"卡在 0%"。
- 1000 文件任务，验证回调数量受节流约束，不随块数线性增长。

### 9.6 回调（针对坑 接-6）

| 用例 | 期望 |
|---|---|
| 正常路径 | 阶段变化与终态全部送达，`seq` 单调 |
| 回调目标返回 5xx | 按退避重试，最终成功 |
| 回调目标全程不可达 | 任务**本身正常完成**；终态可通过查询接口取到；日志有 ERROR 记录 |
| 回调目标不在白名单 | 提交时同步拒绝，不创建任务 |
| 回调目标返回 302 | **不跟随**，视为失败 |
| 签名 | spinfield 侧能用共享密钥验证通过；篡改载荷后验证失败 |
| 终态载荷 | 字段足以让 spinfield 直接落库，无需二次查询 |

### 9.7 取消（对应 SR-9）

| 用例 | 期望 |
|---|---|
| transferring 中取消 | 任务转 canceled，版本与快照标识**保持原样**，发出终态回调 |
| publishing 中取消 | 拒绝，`IMPORT_TASK_NOT_CANCELABLE` |
| 已终态的任务取消 | 拒绝或幂等返回，需在文档中写明选定语义 |
| 取消后重新提交同一 taskId | 正常重新执行，复用已暂存内容 |

### 9.8 源文件保护（对应 SR-3.4、SR-3.5）

- 任务成功、失败、取消三种情况下，验证源文件**均未被删除、移动、改名、截断、改权限**。
- 读取期间截断源文件 → 拒绝，不产生生效内容。
- 读取期间原地覆写源文件 → 整体摘要校验拦下，不产生生效内容。

### 9.9 并发与资源（对应 SR-10）

| 用例 | 期望 |
|---|---|
| 超过任务并发上限 | 按选定语义排队或明确拒绝，不静默丢弃 |

### 9.10 回收（对应 SR-11）

## 13. 待决问题

> 这些问题**必须在动工前拍板**。实现者不得自行决定——每一条都会影响已发布数据的可迁移性或系统的安全边界。

### D-1 字节来源模式（P 还是 R）🔴

这不是一个偏好问题，而是**一个事实问题加一条推论**。

**推论**（见 §3.1.1）：上传接口只监听回环 ⟹ spinfield 后端必须与 dingospeed 同机 ⟹ dingofs 已挂载在这台主机上 ⟹ dingospeed 也能读到同一路径。**模式 P 可行必然蕴含模式 R 可行**，且模式 R 少一次全量回环传输。

**因此唯一需要查清的事实是：dingospeed 进程在它所在的主机上，能不能读到 dingofs 上的那个路径。** 在 dingospeed 所在主机上执行：

```bash
findmnt -T /要验证的/dingofs/路径
```

需要确认并记录以下五项：

| # | 要确认的事实 | 怎么查 |
|---|---|---|
| 1 | 该路径确实位于一个已挂载的文件系统上，且不是本地盘 | `findmnt -T <路径>`、`df -Th <路径>` |
| 2 | 文件系统类型（是否 FUSE） | `findmnt -no FSTYPE -T <路径>` |
| 3 | **dingospeed 的运行用户**能读到该路径（不是 root 能读） | `sudo -u <dingospeed用户> head -c 1 <某个文件>` |
| 4 | 挂载是每节点独立还是全局共享同一份 | 在另一节点上查同一路径，比对 inode 与内容 |
| 5 | `realpath` / 符号链接 / `/proc/self/fd` 回查在该文件系统上行为正常 | 见坑 接-9，需实测 |

**判定**：

- 1~3 全部成立 → **选模式 R**，按环 7 实现按路径入库。
- 3 不成立（挂载存在但 dingospeed 用户读不到）→ 优先**调整挂载权限**，而不是退回模式 P。这是运维配置问题，不是架构问题。
- 挂载根本不存在于该主机 → 那么 spinfield 后端也读不到，**模式 P 同样不可行**，需要先解决挂载，两条路都堵着。
- 5 存在问题 → **先解决坑 接-9，再动工**，不要降级校验。

> **如果最终因为某种约束必须让 spinfield 后端与 dingospeed 分机部署**，那不是在 P 和 R 之间选，而是同时推翻了回环监听（主文档 §4.1 硬性约束）与"文件在本机"两个前提。届时需要单独评估凭证、TLS 与网络边界，属于另一个需求，不在本文档范围内。

| **D-4** | 回调地址来源 | (a) 每个任务在请求中携带（白名单校验）；(b) 只用配置中的固定地址 | **(a) + 白名单**。灵活性有实际价值（多环境、灰度），白名单足以消除 SSRF 风险 |
| **D-5** | spinfield 是否需要 dingospeed 提供任务列表/历史查询 | (a) 不提供，业务态归 spinfield；(b) 提供 | **(a)**。见 SR-7.4。若 spinfield 确有需求，应在 spinfield 侧落库，而不是让 dingospeed 长期持有业务态 |
| **D-6** | 大文件的进度粒度 | 块级（8MB）是否足够 | 倾向足够。块是持久化的最小单位，比它更细的进度**在语义上无法保证正确**（坑 接-3） |

## 14. 给实现者的最后提醒

1. **改的是"谁触发、字节从哪读、过程怎么被看见"，不是"字节怎么写"**。落盘链路一行都不该动。如果你在改块写入或清单序列化，回去看 §3.1.3。
2. **等价性仍然是最便宜的检验器**。同一批文件走路径入库和走 defer+publish，快照标识必须逐字符相同。先把它跑通，再做别的。
3. **源侧安全是这个增量唯一不允许"大概没问题"的地方**。它把一个写入接口变成了一个读取接口，风险性质完全变了。
4. **不要持久化任务状态**。这是第三次同样的坑：进度从磁盘推导，任务丢了就重提交。持久化换来的一致性问题远大于它省下的重试成本。
5. **不要删源文件**。哪怕成功了、哪怕磁盘紧张、哪怕只是移动一下。
6. **baseCommit 必须在锁内校验**，否则它只是一个安慰剂。
7. **能同步告知的错误不要异步化**。
8. **接口复杂度的检验标准**：spinfield 提交一次，此后只被动接收。要求它逐个文件调用、或者再调一次发布，都说明设计跑偏了。
9. **实现完成后先自问三件事**：源根之外的文件有没有任何一条路径能被读进缓存区？两条入库路径的快照标识一样吗？进程重启后重提交，结果和一次跑完一样吗？
