## 0. 这份文档怎么读

### 0.1 与主需求文档的关系

这是一份**增量需求**，不是重写。主需求文档 [model-upload-requirements.md](./model-upload-requirements.md) 的全部内容**继续有效**，本文档只描述在其之上新增的部分。

凡是主文档中已经确定的约束（命名空间、路径安全、摘要必填、回环监听、防淘汰、下载侧复用、快照标识由清单确定性计算……），本文档**一律不重复陈述，也一律不放宽**。出现冲突时以主文档为准，除非本文档明确写了"本期修改"。

标记规则沿用主文档：**【硬性约束】** 不可协商，**【明确不做】** 是范围边界。

### 0.2 一句话总结

> 这个增量的本质是：**把"生效"这个动作从"每传完一个文件"上摘下来，改成"一批文件传完之后做一次"**。
>
> 文件内容**仍然一个一个传**——断点续传、大文件、内存无关、一条 curl 传一个文件，这些全部原样保留。变的只是"什么时候让它们对下载方可见"。
>
> 如果你发现自己在设计"一个请求里塞多个文件"的传输格式，方向就错了（见坑 批-1）。

### 0.3 动工前置条件

- 当前分支基线：`single-file-upload` 分支上的环 1~环 4 产物，`go build ./...` 与 `go test ./...` 可正常运行。
- 本增量在 `batch-file-upload` 分支上进行。
- 进入每一个新环之前与完成之后，都必须保持 `go build ./...` 与 `go test ./...` 可正常运行。

## 1. 背景与目标

### 1.1 背景：逐个提交带来的副作用

当前单文件接口每成功传完一个文件，就会立即重建该版本的完整清单、算出一个新的快照标识、并把版本标签指向它。逐个上传 N 个文件，因此会产生 **N 次生效**。功能上是对的（主文档 §9.2 已验收），但带来一组副作用：

| # | 副作用 | 说明 |
|---|---|---|
| 1 | **N 个快照标识，其中 N-1 个是中间态** | 只有最后一个被版本标签指向，其余全部是"传到一半"的仓库快照 |
| 2 | **中间态元数据永久残留** | 每个快照标识都会在磁盘上留下一份清单与版本元数据。这些残留**不会被任何机制回收**：磁盘清理任务只回收未完成上传的暂存文件，而 `dingo-local` 命名空间本身又被排除在缓存淘汰之外（FR-9） |
| 3 | **"幽灵版本"可被解析** | 记录过中间快照标识的客户端，之后仍能用它解析出一个**只包含部分文件**的仓库，且系统认为它完全合法 |
| 4 | **清单写入量随规模平方增长** | 每次生效都要重写一次全量清单，逐个传 N 个文件写入的清单字节数是 O(N²) |
| 5 | **没有整仓原子性** | 传到第 k 个文件时失败，仓库停在"发布了 k 个文件"的状态，没有回滚，只能靠调用方重跑补齐 |
| 6 | **中间态对下载方可见** | 主文档 §11 已作为已知限制接受：用户可能拉到一个只有部分文件的模型 |
| 7 | **调用方拿不到确定的最终标识** | 每次上传返回一个不同的快照标识，传完之前无法知道哪个是最终值 |

### 1.2 目标

提供**一次提交多个文件**的能力，使得：

- 最终效果与"逐个提交同样这批文件"**完全一致**（见 BR-2）；
- 整批文件**一次生效**，只产生一个快照标识；
- §1.1 中第 1~7 条副作用全部消除或明确收敛。

### 1.3 一句话价值

> 单文件接口解决的是"**把一个文件安全地放到正确位置**"。这个增量解决的是"**让一组文件同时出现**"。前者是地基，后者是地基之上的第一层楼，不再往上加。

## 2. 名词约定

沿用主文档 §2，新增：

| 名词 | 含义 |
|---|---|
| **发布（publish）** | 把一组已经完整落盘的文件一次性纳入版本清单、生成新快照标识、并让版本标签指向它的那个动作。即主文档中的"生效"，只是粒度从单文件变成一组 |
| **暂缓生效** | 一次上传只把内容完整落盘并通过摘要校验，但**不**重建清单、不产生新快照标识、不改变版本标签指向 |
| **待发布内容** | 已经完整落盘并通过摘要校验、但尚未被任何版本清单引用的内容 |
| **发布清单** | 发布请求中声明的这一批文件（每项含仓库内路径、完整摘要、完整字节大小） |

## 3. 范围

### 3.1 本期要做

1. 上传接口支持**暂缓生效**：一次调用只落内容，不触发发布。
2. 一个**发布能力**：以一份发布清单为输入，一次性让这批文件全部生效，只产生一个快照标识。
3. 发布的**原子性**：要么整批生效，要么完全没发生。
4. 发布与现有并发控制、覆盖语义、幂等语义的正确衔接。
5. **待发布内容的可见性控制与回收**（见 BR-6）。
6. 与逐个上传的**等价性验证**（见 BR-2）。

### 3.1.1 【硬性约束】批量的是"发布"，不是"传输"

**文件内容必须继续沿用现有的单文件传输方式：一次 HTTP 调用传一个文件，请求体是该文件的字节流。**

**【明确不做】**：
- 不做 `multipart/form-data` 一个请求塞多个文件；
- 不做 tar / zip 等归档上传与服务端解包；
- 不做任何"一次请求传多个文件内容"的传输格式。

> **为什么这是硬性要求**：主文档 FR-2 要求在**写第一个字节之前**就知道每个文件的完整摘要与大小（存放位置由摘要决定）。任何"一个请求多个文件"的形态，都要么放弃这个前提，要么把每个文件的摘要塞进一个自定义的多文件协议头里——那等于自己发明一套归档格式。
>
> 同时，断点续传是按单个文件的字节偏移定义的（FR-4）。多文件打包传输一旦中断，"从哪里继续"这个问题就不再有简单答案，主文档 §3.3.1 明确推迟的分块上传复杂度会从这里绕回来。
>
> **传输侧已经是对的，不要动它。** 这个增量的全部改动应当集中在"何时发布"上。

### 3.1.2 【硬性约束】单文件接口的现有对外行为不得改变

不带任何新参数调用现有上传接口时，行为必须与增量前**逐字节一致**：传完即生效、返回新的快照标识。

暂缓生效必须是**显式声明**才进入的路径。默认行为不变。

> **为什么**：主文档 §4.2 的接口复杂度检验标准是"一条 curl 完成一次完整上传"。单文件场景不应该因为增加了批量能力而变成两条。

### 3.1.3 【硬性约束】允许改什么、不允许改什么

| 层次 | 本增量的要求 |
|---|---|
| 内容落盘（写 blob、摘要校验、断点续传、块位图） | **必须原样复用**，不允许分叉出批量专用的写入路径 |
| 清单重建与快照标识计算 | **允许**从"一次接受一个文件"扩展为"一次接受一组文件"，但计算规则不得改变（见 BR-2） |
| 发布时机 | **本增量的改动全部集中在这里** |
| 下载侧的任何行为 | **不允许改变** |
| 单文件上传与进度查询的默认行为 | **不允许改变** |

### 3.2 【明确不做】

| 不做的事 | 原因 |
|---|---|
| 一个请求传多个文件的内容（multipart / 归档） | 见 §3.1.1 |
| 服务端维护"批次会话"状态（批次 ID、批次表、批次进度文件） | 见 BR-1.3。理由与主文档 FR-4.5 完全一致 |
| 批次级的进度查询接口（"这个批次还差哪些文件"） | 调用方本来就持有完整清单，逐个查现有进度接口即可 |
| 服务端并行编排（服务端主动拉取、服务端调度多文件） | 并行由调用方脚本决定，服务端只受现有并发上限约束 |
| 从版本中**删除**文件、整仓替换语义 | 发布是**合并**语义（见 BR-2.2）。删除仍属主文档 §3.3 的预留项 |
| 批次的回滚 / 撤销已发布的快照标识 | 同上，属删除能力 |
| 跨版本标签、跨仓库的批量发布 | 一次发布只作用于一个 `repoType/org/repo/revision` |
| 批量上传的专用客户端 / SDK | 沿用主文档 §3.2，通用 HTTP 工具即可 |
| 事务日志、两阶段提交、一致性中间件 | 沿用主文档 FR-3.3 |
| 引入新的外部依赖 | 沿用主文档 §3.2 |

### 3.3 本期不做但需要预留可能性

- **删除已发布版本中的某个文件**（发布的合并语义不应堵死将来加"替换语义"）。
- **分块上传**（主文档 §3.3.1 的两条硬性约束继续有效，本增量不得违反）。

## 4. 接口形态

> 本节约定**形态与检验标准**，不指定具体路径、参数名和响应结构——那些由实现者设计，但需在交付文档中写清。

### 4.1 网络边界

沿用主文档 §4.1：发布接口与上传、进度查询一样，**只允许监听本机回环地址**，凭证通过请求头传递，与上传使用同一个凭证。

### 4.2 调用形态与复杂度检验标准

**一次 N 个文件的批量发布，必须能用 N + 1 条 curl 命令完成**：N 条上传（每条一个文件，声明暂缓生效），加 1 条发布。

- 其中任何一条上传中断，续传仍是"查进度 + 继续传"两条命令，不受批量影响。
- 超出这个复杂度，说明接口设计跑偏了。

**发布请求需要携带**：

- 仓库类型、组织名、仓库名、版本标签（定位到唯一一个版本）；
- **发布清单**：本批次的每个文件的仓库内路径、完整摘要、完整字节大小；
- 覆盖声明（见 BR-5）。

**发布响应需要包含**：

- 本次发布后的**快照标识**（唯一一个）；
- 本批次实际纳入的文件数量；
- 足以让调用方确认"这批确实全生效了"的信息。

## 5. 使用场景

### 场景 F：算法工程师一次发布一个完整模型（本增量的主场景）

1. 工程师手上有一个目录，含若干文件与子目录。
2. 脚本遍历目录，为每个文件算出 SHA-256 和大小，逐个调用上传接口，**声明暂缓生效**。此阶段下载方看不到任何变化。
3. 全部传完后，脚本用同一份清单调用一次发布。
4. 发布成功，得到**一个**快照标识。此刻整个仓库版本一次性对下载方可见。
5. 用户拉取，拿到的是**完整**的仓库，不存在"拉到一半的模型"的时间窗。

### 场景 G：批量上传中途失败

1. 传到第 7 个文件时脚本挂掉。
2. 此时**下载方看到的仍然是这次批量之前的状态**——没有半个仓库，也没有新的快照标识。
3. 工程师重跑脚本。已经传完的文件走幂等快路径直接跳过，未传完的续传。
4. 全部传完后发布，结果与一次跑完**完全一致**。

### 场景 H：向已发布的版本追加一批文件

1. 用同一个版本标签，暂缓生效地传若干新文件，然后发布。
2. 新快照标识对应的清单，包含**此前已生效的全部文件 + 本批次的全部文件**。
3. 老文件一个不少，新文件一个不多。

### 场景 I：混用

在同一个版本标签下，既用过单文件即时生效上传，也用过批量发布。两者互不冲突，最终清单正确。

## 6. 功能需求

### BR-1 暂缓生效与发布 【硬性约束】

#### 6.1.1 暂缓生效的语义

一次声明了暂缓生效的上传，成功时必须做到：

| 项 | 要求 |
|---|---|
| 内容落盘 | 与即时生效上传**完全相同**：同样的缓存格式、同样的摘要校验、同样的块位图状态 |
| 清单 | **不重建** |
| 快照标识 | **不产生新的** |
| 版本标签指向 | **不改变** |
| 对下载方 | **完全不可见**——既拉不到这个文件，也观察不到任何元数据变化 |
| 响应 | 必须能让调用方明确区分"内容已就绪，等待发布"与"已生效" |

断点续传对暂缓生效的上传**同样适用**，行为与现有一致。

#### 6.1.2 发布的语义

一次发布必须做到：

1. 校验发布清单中的**每一个**文件的内容确实已经完整落盘（大小与摘要都对得上）。**任何一个不满足，整次发布失败，不产生任何副作用。**
2. 把发布清单**合并**进该版本的现有清单（见 BR-2.2）。
3. 由合并后的完整清单算出**一个**快照标识。
4. 让版本标签**原子地**指向该标识。
5. 整个过程只产生**一个**新的快照标识及其对应的一份元数据。

#### 6.1.3 【硬性约束】不得引入批次状态存储

**【明确不做】**：不要建批次表、不要写批次状态文件、不要在内存里维护批次会话、不要发放批次 ID。

**发布请求必须自带完整的发布清单**，服务端不需要"记得"之前哪些上传属于哪一批。

> **理由与主文档 FR-4.5 完全一致**：一是重复造轮子——"这个文件是否已就绪"完全可以从落盘内容本身判断（现有进度查询就是这么做的）；二是独立状态与实际落盘内容之间必然出现不一致（进程崩在"传完"和"记状态"之间），那种不一致极难排查。
>
> **对调用方零负担**：路径、摘要、大小三样东西本来就是上传时的必填项，调用方一定持有。把它们再声明一次不增加任何使用成本，却换来了服务端完全无状态、崩溃后天然可恢复。
>
> **额外收益**：发布清单同时起到"调用方声明我这批要发什么"的作用，服务端据此校验，能挡住"少传了一个文件却以为发全了"这类错误（见坑 批-2）。

---

### BR-2 与逐个上传的等价性 【硬性约束 —— 核心验收项】

#### 6.2.1 等价性定义 🔴

**对同一组文件，"逐个即时生效上传"与"暂缓生效上传 + 一次发布"，最终状态必须完全一致。**

具体到可验证的层面：

| 项 | 要求 |
|---|---|
| **最终快照标识** | 两条路径产生的快照标识必须**逐字符相同** |
| **最终清单** | 内容与顺序完全一致 |
| **版本元数据** | 逐字节一致 |
| **下载侧行为** | 整仓拉取、单文件拉取、分段下载、目录结构、内容校验，全部一致 |
| **磁盘上的内容文件** | 完全一致 |

> **为什么快照标识必须逐字符相同，这不是苛求**：现有快照标识就是**由完整清单确定性计算**出来的（主文档 FR-5.2）。只要发布产出的清单和逐个上传产出的最终清单是同一份，标识就必然相同。**标识对不上，等价性就一定在别的地方也不成立**——它是一个成本极低、灵敏度极高的检验器。
>
> 反过来说，如果实现时为批量发布改了清单的排序规则、序列化方式或字段，标识就会漂移。那意味着同一批内容用两条路径进系统会得到两个不同的版本，客户端会被迫重下一遍（主文档 坑 12 的变体）。

#### 6.2.2 发布是合并语义 【硬性约束】

发布清单**不是**该版本的完整清单，而是"本批次新增或覆盖的部分"。

服务端必须以该版本**当前已生效的清单**为基础，用发布清单中的条目**按路径覆盖或追加**，得到合并后的完整清单。

**发布清单中没有提到的已生效文件，必须原样保留。**

> **为什么必须是合并而不是替换**：这正是等价性（6.2.1）的要求——逐个上传本来就是累积的。同时它也是主文档坑 3 的批量变体：如果发布时直接把发布清单当成完整清单写下去，向已有版本追加一批文件就会把老文件全部抹掉。
>
> "整仓替换"是一种**删除能力**，属于主文档 §3.3 的预留项，本期【明确不做】。

#### 6.2.3 空变更

若合并后的清单与当前清单完全相同（这批文件早就全部生效且内容未变），发布必须成功返回，且**快照标识保持不变**、不重写元数据。

---

### BR-3 内容上传阶段保持不变 【硬性约束】

暂缓生效的上传，除了"不触发发布"之外，其余行为与现有单文件上传**完全一致**：

- 身份校验、路径安全、命名空间、格式能力上限、无界写入防护——全部沿用；
- 摘要在内容完整之后**整体重算**，不做流式累加（主文档 §3.3.1 第 1 条）；
- 写入路径不得做成只能追加（主文档 §3.3.1 第 2 条）；
- 断点续传的可续传偏移量仍从缓存文件块位图推导；
- 内存占用与文件大小无关；
- 同一文件的并发上传仍然互斥。

**【明确不做】**：不要为暂缓生效路径新写一份落盘逻辑。

---

### BR-4 发布的原子性与并发 【硬性约束】

#### 6.4.1 原子性

1. 发布要么完全成功（整批文件可下载、清单已合并、快照标识已更新、版本标签已切换），要么完全没发生。
2. 发布失败不得损坏该版本中**已经生效的任何文件**。
3. 进程在发布过程中的任意时刻崩溃，重启后系统看到的状态必须是**合法的**：要么是发布前的状态，要么是发布完成后的状态。**不允许出现"清单里有但文件不存在"、"半截元数据"、"快照标识更新了但版本标签没切"** 这类中间态。

> 沿用主文档 FR-3.3 的降低要求：不要求穷举崩溃点，但**最终那一步"让内容对外可见"的动作必须是原子的**。

#### 6.4.2 并发

1. 同一个仓库、同一个版本标签，**同一时刻只允许一个发布在进行**。第二个请求必须被明确拒绝并告知原因，不排队、不交错。
2. 发布与该版本下正在进行的**内容上传**可以并存（上传不改清单），但发布只对"发布清单里已完整落盘"的文件负责。
3. 发布进行中，该版本**已生效文件的下载不受影响**。
4. 不同版本标签、不同仓库的发布互不影响。
5. **即时生效上传与发布之间也必须互斥**——两者都会重建清单，是同一个争用点（主文档 坑 8）。

#### 6.4.3 规模

发布清单的条目数上限应与主文档 §9.13 给出的单仓库文件数上限对齐。超过上限必须明确拒绝，不得静默截断。

---

### BR-5 覆盖与幂等在批量下的语义

| 情况 | 行为 |
|---|---|
| 发布清单中的文件在当前清单中不存在 | 正常追加，不算覆盖 |
| 已存在，且路径/摘要/大小完全相同 | 视为无变化，不算覆盖 |
| 已存在，摘要不同，**未显式声明覆盖** | **整次发布拒绝**，并明确告知是哪些路径冲突 |
| 已存在，摘要不同，**显式声明覆盖** | 允许，合并后清单、快照标识同步更新 |
| **发布清单内部有两个条目指向同一路径** | **拒绝**，这是调用方的清单错误，不要试图择一（见坑 批-5） |

**覆盖声明作用于整次发布**，不做逐文件的覆盖声明。

> **为什么冲突时要整次拒绝而不是发布能发的那部分**：部分发布会重新引入本增量要消除的"中间态"，而且调用方无法从结果中判断哪些生效了。要么全成，要么全不成，这是批量的意义所在。

---

### BR-6 待发布内容的可见性与回收 【硬性约束】

#### 6.6.1 可见性

待发布内容对下载方**必须完全不可见**：既不能被单文件拉取到，也不能出现在任何版本的清单中，也不得让任何快照标识指向它。

#### 6.6.2 回收 🔴

**这是本增量引入的一类新残留，必须专门处理。**

暂缓生效上传成功后，内容已经完整落盘、通过了摘要校验，但可能**永远等不到那次发布**（脚本挂了、工程师放弃了、改用别的清单了）。这类内容：

- **不是**未完成的上传残留——现有清理任务只回收"未完成的暂存文件"，够不着它；
- **不会**被磁盘淘汰机制清理——`dingo-local` 命名空间被整体排除在淘汰之外（主文档 FR-9）；
- 因此在当前机制下会**无限累积**。

**要求**：

1. 必须能识别"已完整落盘但未被任何版本清单引用"的内容。
2. 这类内容必须有**保留期限**（可配置），期限内可被发布或续用，超期可被回收。
3. 回收**绝对不得误删**任何被清单引用的内容——包括被**其他版本标签**、**其他快照标识**引用的内容。内容是按摘要寻址的，同一份内容可能被多个版本共享。
4. 回收动作要有日志，可诊断。

> **为什么保留期不能太短**：一个 30GB 的模型批量上传可能跨小时甚至跨天（含中断续传）。保留期必须明显大于一次完整批量上传的正常耗时，取值可参照现有的暂存保留期（默认 168 小时）。

**【明确不做】**：不做引用计数表、不做垃圾回收的精细策略、不做容量配额。能识别、能清理、不无限增长即可（沿用主文档 §3.2）。

---

### BR-7 错误反馈

沿用主文档 FR-8 的分类原则，新增以下必须可区分的失败类别：

| 类别 | 说明 |
|---|---|
| 发布清单为空 / 条目数超上限 | 参数问题 |
| 发布清单中某些文件的内容**尚未完整落盘** | 必须**明确列出是哪些路径**，让调用方知道该补传哪几个 |
| 发布清单中某些文件的摘要或大小与已落盘内容**对不上** | 内容问题，列出冲突路径 |
| 发布清单中存在**重复路径** | 参数问题，列出重复路径 |
| 与已生效文件冲突、未声明覆盖 | 冲突问题，列出冲突路径 |
| 同一版本已有发布在进行中 | 冲突问题 |

**【明确不做】**：不做发布专用的监控面板、不引入新的指标体系。

---

### BR-8 兼容性 【硬性约束】

1. 现有单文件上传接口不带新参数时，行为**逐字节不变**。
2. 现有进度查询接口行为不变。
3. 下载侧的任何对外行为不变。
4. ModelScope 通道不受任何影响。
5. 主文档环 1~环 4 的**全部自动化测试必须继续通过，且不允许为迁就新功能而修改其断言**。

---

## 7. 已知风险与踩坑点

> 每条按 **是什么 / 怎么来的 / 解决方向** 说明。

### 坑 批-1：把"批量"做成了"一个请求传多个文件" 🔴

**是什么**
实现者看到"批量上传"，第一反应是设计一个能一次传多个文件的请求格式（multipart、tar、自定义分隔）。结果是断点续传彻底失效，协议复杂度翻倍，而且和"摘要必须预先声明"直接冲突。

**怎么来的**
"批量上传"这个词的字面含义指向传输层，但真正的痛点在**发布层**（§1.1 的 7 条副作用没有一条来自"传输是一个一个做的"）。

**解决方向**
见 §3.1.1。传输层完全不动，只把发布从单文件上摘下来。**动手前先确认自己改的是"何时生效"，不是"怎么传"。**

---

### 坑 批-2：发布时不核对内容是否真的在磁盘上

**是什么**
发布成功了，清单里有 20 个文件，但其中 3 个下载时报找不到，或者拉下来是坏的。

**怎么来的**
发布请求是调用方声明的清单。如果服务端信任这份声明直接写清单，那么"调用方少传了一个文件却把它写进了发布清单"、"某个文件传了一半就被中断"、"某个文件的内容被外部清理删掉了"都会产生"清单里有但文件不存在"的破损状态——这正是主文档 FR-3.3 明令不允许出现的状态。

**解决方向**
发布前**逐个校验**清单中每个文件的内容确实完整落盘（大小与块位图都对）。任何一个不满足，整次发布失败，并在错误信息中列出是哪些路径。

**验收**：必须专门构造"发布清单中含一个从未上传过的文件"和"含一个只传了一半的文件"两类用例。

---

### 坑 批-3：待发布内容成为永不回收的垃圾 🔴

**是什么**
系统跑一段时间后磁盘被吃满，排查发现大量内容文件既不属于任何版本，也没有任何机制会去删它们。

**怎么来的**
见 BR-6.2：这类内容在现有机制里处于三不管地带——不是未完成的暂存文件（清理任务够不着），又在 `dingo-local` 命名空间里（防淘汰保护着它）。批量上传把"传完但没发布"从一个罕见的崩溃残留，变成了**正常流程中长期存在的状态**，累积速度完全不同。

**解决方向**
见 BR-6.2。识别未被引用的内容，按保留期回收。

**特别注意**：内容是**按摘要寻址**的，同一份内容可能同时被多个版本标签、多个快照标识引用。判断"是否被引用"时必须扫全，**误删一个被引用的 blob 就是数据丢失**——而且因为 `dingo-local` 是唯一发布源，删了就没有了（主文档 坑 13 的教训）。

---

### 坑 批-4：批量发布的快照标识和逐个上传对不上 🔴

**是什么**
同一批文件，用批量发布和用逐个上传，得到了两个不同的快照标识。客户端因此认为是两个不同的版本，白白重下一遍；如果两条路径在生产中混用，还会出现"内容一样却反复更新"的怪象。

**怎么来的**
快照标识是由清单确定性计算出来的。批量路径如果自己写了一套清单构建逻辑——排序规则不同、序列化方式不同、字段顺序不同、合并时的去重策略不同——标识就会漂移。这类偏差**在单独测批量时完全测不出来**，因为批量路径自己内部是自洽的。

**解决方向**
清单的合并、排序、序列化与标识计算，**批量与单文件必须走同一套代码**，不允许复制一份改改用（主文档 §8"可维护性"）。

**验收**：见 §9.1，必须直接对比两条路径产出的快照标识**逐字符相同**。这是本增量最重要的一条验收。

---

### 坑 批-5：发布清单内部自相矛盾

**是什么**
发布清单里两个条目指向同一个仓库内路径，但摘要不同。服务端择一写入，调用方拿到成功响应，实际生效的却不是他以为的那个文件。

**怎么来的**
调用方脚本的 bug（大小写、路径归一化、目录遍历重复）。服务端如果宽容处理，错误会被静默吞掉。

**解决方向**
明确拒绝，列出重复路径。**不要择一，不要"后者覆盖前者"**——在这里容错等于制造坏数据（沿用主文档 坑 10 的原则）。

---

### 坑 批-6：发布把已有文件抹掉了

**是什么**
向一个已经有 10 个文件的版本追加 2 个新文件，发布之后整仓拉取只剩下 2 个。

**怎么来的**
把发布清单当成了该版本的完整清单直接写下去。这是主文档坑 3 在批量场景下的原样重演——只不过这次一次就能抹掉全部。

**解决方向**
见 BR-2.2：发布是合并语义，必须以当前已生效清单为基础。

**验收**：必须构造"先发布一批，再发布另一批"的用例，验证两批文件全部都在。单次发布的用例测不出这个坑。

---

### 坑 批-7：发布与上传并发时清单丢条目

**是什么**
一边在批量发布，一边有人用即时生效的方式传了个文件。最终清单里少了其中一个。

**怎么来的**
两者都要"读当前清单 → 合并 → 写回"。如果不在同一把锁下，各自基于陈旧清单重建，后写的会覆盖先写的。这就是主文档坑 8，只是参与方从"两个单文件上传"变成了"发布 vs 单文件上传"。

**解决方向**
见 BR-4.2 第 5 条：即时生效上传与发布必须共用同一个版本级互斥。

**验收**：专门构造两者并发的用例。

---

## 8. 非功能需求

| 项 | 要求 |
|---|---|
| **性能** | 一次发布 N 个文件的元数据写入量必须是 **O(N)** 级别，不得随发布次数或仓库文件数出现平方增长。这是本增量的量化目标之一（对应 §1.1 副作用 4） |
| **内存** | 沿用主文档：内存占用与被上传文件大小无关。发布阶段的内存占用与清单条目数成线性，不得把文件内容读进内存 |
| **稳定性** | 发布过程的任何异常中断，都不得损坏已生效数据 |
| **兼容性** | 见 BR-8 |
| **部署** | 沿用主文档：单节点、不引入新的外部依赖 |
| **新增配置项** | 预期包括：待发布内容的保留期限、发布清单条目数上限。实现者需在交付文档中完整列出，并说明与现有 `upload.*` 配置的关系 |
| **可维护性** | 清单合并、排序、序列化、快照标识计算：批量与单文件**共用同一套实现**（针对坑 批-4） |

## 9. 验收标准与测试目标

> 本节说明**要验证什么**，不规定测试代码怎么写。前提：`go build ./...` 与 `go test ./...` 基线正常。

### 9.1 等价性（核心验收，针对坑 批-4）🔴

- 准备一组文件（**含子目录、含多级目录**，N ≥ 5）。
- 路径 A：在版本标签 `va` 下逐个即时生效上传。
- 路径 B：在版本标签 `vb` 下逐个暂缓生效上传，然后一次发布。
- 验证：
  - 两个版本解析出的**快照标识逐字符相同**；
  - 两份清单完全一致；
  - 两个版本的整仓拉取结果**逐字节一致**；
  - 磁盘上的内容文件一致。
- **模型与数据集两种类型都要跑**。
- **在线模式与离线模式都要跑**（沿用主文档针对坑 1 的要求）。

### 9.2 完整性（针对坑 批-6）

- 批量发布 N 个文件（含子目录），整仓拉取，验证**文件数量、目录结构、内容与原始目录逐字节一致**，一个不多一个不少。
- 再发布第二批，验证两批文件**全部都在**，快照标识变成新的。
- 用标准客户端（`huggingface_hub`）执行，不能只用 curl。

### 9.3 中间态不可见（本增量的主要价值，针对 §1.1 副作用 1/6/7）

- 暂缓生效地传若干文件，**在发布之前**验证：
  - 整仓拉取拿不到这些文件；
  - 版本标签解析出的快照标识**没有变化**；
  - 单独拉取这些文件拿不到；
  - 磁盘上**没有产生任何新的快照标识对应的元数据**。
- 发布之后，上述内容一次性全部可见。
- **计数验证**：批量发布 N 个文件，全过程只应产生 **1 个**新的快照标识。逐个上传作为对照组应产生 N 个。这是对副作用 1 与 2 的直接量化验收。

### 9.4 发布前置校验（针对坑 批-2）

| 用例 | 期望 |
|---|---|
| 发布清单含一个从未上传过的文件 | 整次拒绝，错误信息列出该路径，**不产生任何副作用** |
| 发布清单含一个只传了一半的文件 | 整次拒绝，列出该路径 |
| 发布清单中某文件的摘要与已落盘内容不符 | 整次拒绝 |
| 发布清单中某文件的大小与已落盘内容不符 | 整次拒绝 |
| 发布清单为空 | 拒绝 |
| 发布清单条目数超上限 | 拒绝，原因明确 |
| 发布清单含重复路径（坑 批-5） | 拒绝，列出重复路径 |
| 上述任一拒绝之后 | 版本标签与快照标识**保持原样**，磁盘上没有新增任何元数据 |

### 9.5 覆盖与幂等（对应 BR-5）

| 用例 | 期望 |
|---|---|
| 发布一批与当前清单完全相同的文件 | 成功，快照标识**不变**，不重写元数据 |
| 批中含一个内容不同的已存在文件，未声明覆盖 | 整次拒绝，列出冲突路径 |
| 同上，声明覆盖 | 成功，下载到新内容，快照标识更新 |
| 批中混合"新增 + 覆盖 + 完全相同"三类文件 | 按上表逐类正确处理，合并后清单正确 |
| 重复执行同一次发布 | 第二次成功且快照标识不变（幂等） |

### 9.6 原子性与崩溃一致性（对应 BR-4.1）

- 发布过程中在关键步骤杀掉进程，重启后验证：看到的要么是发布前状态，要么是发布完成后状态；**不出现半截元数据、不出现"清单里有但文件不存在"、不出现"标识更新了但标签没切"**。
- 发布失败（任意原因）后，验证该版本已生效文件的下载**完全不受影响**。
- 场景 G 全流程：传到一半杀掉，重跑（幂等跳过已传的 + 续传未完的），发布，结果与一次跑完**逐字节一致**。

### 9.7 并发（对应 BR-4.2，针对坑 批-7）

| 用例 | 期望 |
|---|---|
| 同一版本并发发起两次发布 | 第二个被明确拒绝，第一个结果正确 |
| 发布进行中，同一版本有即时生效的单文件上传 | 最终清单**同时包含两者**，快照标识反映最终内容 |
| 发布进行中，该版本已生效文件的下载 | 不受影响 |
| 不同版本标签并发发布 | 互不影响，各自正确 |
| 暂缓生效上传与发布并发（上传的文件不在本次发布清单里） | 互不影响 |

### 9.8 断点续传在暂缓生效路径下不退化（对应 BR-3）

- 暂缓生效地上传一个大文件，中断，查进度，续传，再发布。验证最终内容逐字节一致。
- 主文档 §9.7 的续传异常路径用例（大小不符、摘要不符、起始位置大于/小于可续传偏移、中途换文件）在暂缓生效路径下**同样必须全部拒绝**。

### 9.9 待发布内容的回收（对应 BR-6.2，针对坑 批-3）

| 用例 | 期望 |
|---|---|
| 暂缓生效上传后不发布，保留期内 | 内容保留，可被发布 |
| 超过保留期且从未被引用 | 可被回收 |
| 内容被某个快照标识引用 | **绝不回收**，无论多久 |
| 内容被**另一个版本标签**引用 | **绝不回收** |
| 同一份内容（同摘要）被多个版本共享，其中一个版本被覆盖 | 仍被引用，**绝不回收** |
| 反复中断的批量上传 | 残留不无限累积 |

> 最后三行是本项的重点。**误删一个被引用的内容就是数据丢失**，必须专门构造用例。

### 9.10 安全（沿用主文档 §9.10）

- 发布接口**从其他机器访问不通**。
- 不带凭证 / 错误凭证 / 服务端未配置凭证时发布 → 拒绝，无落盘副作用。
- 发布清单中的路径字段包含 `..`、绝对路径、反斜杠、盘符、控制字符 → 全部拒绝，且确认目标目录之外没有产生任何文件。
- 发布到 `dingo-local` 之外的组织名 → 拒绝。
- 非法仓库类型 → 拒绝。

> 发布清单是一个**新的、批量的**不可信输入入口。主文档 §9.10 的路径逃逸矩阵必须在这个入口上**重跑一遍**，不能因为"上传时已经校验过"就跳过。

### 9.11 规模与性能（对应 §8）

- 单次发布 1000 个文件，记录耗时。
- **对比测量**：1000 个文件用批量方式 vs 逐个方式，记录两者的元数据写入量与总耗时，验证批量方式的元数据写入量是 O(N) 而非 O(N²)。

## 11. 已知限制（必须写入交付文档）

| 限制 | 说明 | 使用方如何规避 |
|---|---|---|
| **批量不减少传输次数** | N 个文件仍然是 N 次 HTTP 上传，批量优化的是发布不是传输 | 无需规避。传输并发由调用方脚本控制，受现有上传并发上限约束 |
| **发布清单需调用方自行维护** | 服务端不记忆批次，调用方必须在发布时提供完整清单 | 脚本在遍历目录算摘要时顺手攒出这份清单即可 |
| **不支持从版本中删除文件** | 发布是合并语义 | 需要一个"干净"的版本时，使用新的版本标签 |
| **发布失败需整批重试** | 不做部分发布 | 内容已落盘的文件重试时走幂等快路径，代价很小 |
| **待发布内容占用磁盘** | 传完未发布的内容会占盘直到发布或超期回收 | 批量上传后及时发布；放弃的批次可等待自动回收 |
| **仍仅支持单节点** | 沿用主文档 §3.1.3 | 同主文档 |

## 13. 给实现者的最后提醒

1. **改的是"何时生效"，不是"怎么传"**。传输层一行都不该动。如果你在设计多文件传输格式，回去看 §3.1.1。
2. **等价性是这个增量的立身之本**。快照标识逐字符相同是一条成本极低的检验——先把它跑通，再做别的。
3. **清单与标识只能有一套实现**。批量复制一份改改用，坑 批-4 立刻成立，而且只在混用两条路径时才暴露。
4. **发布是合并，不是替换**。写清单前先读当前清单（坑 批-6）。
5. **不要建批次状态**。发布请求自带清单，服务端保持无状态——理由和主文档"不要建进度表"完全一样。
6. **不要相信发布清单**。它是调用方声明的，落盘校验必须自己做一遍（坑 批-2）。
7. **待发布内容是新的垃圾来源，而且没有任何现有机制会去清它**（坑 批-3）。回收时反过来又要极度小心误删——`dingo-local` 是唯一发布源，删了就没有了。
8. **接口复杂度的检验标准**：N 个文件 = N 条上传 curl + 1 条发布 curl。超出说明设计复杂了。
9. **实现完成后，先自问 BR-2 的判定标准**：同一批文件走两条路径进系统，快照标识一样吗？不一样就回去改。
