## 0. 这份文档怎么读

这份文档描述的是**功能应该做成什么样子**,以及**做的过程中已知会踩到哪些坑**。

它**不规定**用什么函数、改哪个文件、用什么数据结构。那些是实现者的判断。

但文档中标记为 **【硬性约束】** 的条目是不可协商的,它们来自对现有系统的调研,违反了功能就跑不通。标记为 **【明确不做】** 的条目同样不可协商 —— 那是范围边界,不是可以"顺手做了"的加分项。

> **给实现者的一句话总结**:这个功能的本质是"**让服务器上凭空出现一个仓库,并且让它看起来和从上游下载下来的一模一样**"。做完之后,**下载侧的文件读取与传输链路应当原样复用,不需要改动**;只允许在元数据解析层增加"本地仓库"分支(见 §3.1.2)。如果你发现自己在大量改写文件传输逻辑,方向就错了。

## 1. 背景与目标

### 1.1 背景

公司内部会频繁地改动和重新训练自研模型。这些模型需要提供给内部用户使用,但它们**不存在于任何公开上游站点(如 HuggingFace)上**,因此现有的"从上游拉取并缓存"的链路完全覆盖不到它们。

目前这些模型的分发靠人工拷贝,存在版本混乱、无法复用现有加速能力、用户需要切换工具等问题。

### 1.2 目标

提供一个**上传通道**,让自研模型和自研数据集能够被放置到服务器上,进入现有的缓存体系。上传完成后:

- 内部用户使用**和拉取公开模型完全相同的工具与命令**即可下载,无需学习新工具、无需切换配置。
- 自研内容享受与公开内容**同等的下载能力**(分段下载、断点续传、整仓拉取等),且这些能力是**复用**来的,不是重新实现的。

### 1.3 一句话价值

> 从第一性原理出发:先把"把文件安全地放到正确位置"这件最基本的事做扎实,后续所有能力(权限细化、审批流、批量上传、集群同步、Web 界面)都可以在这个接口之上叠加。**本期只做这个地基,不做地基之上的任何楼层。**

## 2. 名词约定

| 名词 | 含义 |
|---|---|
| **仓库(repo)** | 一个模型或数据集的整体,由"组织名/仓库名"两级标识 |
| **仓库类型** | 模型(models)或数据集(datasets),两种都要支持 |
| **版本标签(revision)** | 调用方使用的**可变**标签,如 `main`、`v1`。它指向某一个快照 |
| **快照标识(commit)** | 仓库某一次内容状态的**不可变**标识。内容一变就必须换一个新的。见 FR-5 |
| **完整摘要** | 对一个文件的**完整内容**计算出的 SHA-256。本功能中它是**必填项**,见 FR-2 |
| **生效** | 上传内容从"不可见"转为"对下载方可用"的那个动作 |
| **上游** | 公开的模型托管站点,即现有系统会去回源拉取的那个远端 |
| **本地仓库** | 通过本功能上传的、在上游并不存在的仓库 |
| **下载侧** | 系统中已经存在的、响应用户下载请求的那部分能力。**本文档中一律特指 HuggingFace 兼容通道**,见 §3.1.1 |

## 3. 范围

### 3.1 本期要做

> **当前进度说明**:本节列的是完整功能目标,不是当前下一步的实现范围。环 1、环 2、环 3、环 4 已经完成,后续只应围绕回归维护与交付使用反馈做小步修正。除非本节明确要求且 §12 当前环覆盖,否则不要提前实现后续环内容。

1. 一个供内部使用的上传接口,**一次调用完成一个文件的上传**。
2. 支持模型(models)和数据集(datasets)两种仓库类型。
3. 上传者身份校验。
4. 上传内容的合法性校验(含完整摘要校验)。
5. 上传内容落盘后,能够被现有下载侧正常提供服务。
6. **大文件的断点续传**:上传中断后,能够从服务端已持久化的位置继续传。
7. 版本标签与快照标识的正确维护(见 FR-5)。
8. 自研内容不被现有磁盘清理机制淘汰(见 FR-9)。
9. 上传过程的基本可观测性(日志、失败原因可诊断)。

### 3.1.1 【硬性约束】服务对象是 HuggingFace 兼容下载通道

**本服务器上并存两条相互独立的下载通道,本功能只服务其中一条。**

| | **HF 兼容通道 ← 本功能的目标** | ModelScope 通道 ← 与本功能无关 |
|---|---|---|
| 存放位置 | 系统的主缓存区 | 另一套独立的缓存目录 |
| 文件形态 | 带内部结构的自定义缓存格式 | 普通文件 |
| 本地元数据(版本信息、文件清单) | **有**,会落盘缓存 | **没有** |
| 能否脱离上游独立服务内容 | **能** | **不能** |

**要求**:上传产出的内容必须落到 **HF 兼容通道**的缓存体系中,§9 的全部下载侧验收也都在这条通道上进行。

**【明确不做】**:不要让上传内容进入 ModelScope 通道,不要为 ModelScope 通道增加任何本地仓库能力。

> **为什么**:ModelScope 通道当前的定位是**纯粹的带缓存反向代理** —— 它的元数据接口(仓库信息、版本列表、文件列表、文件树)全部是无条件转发给上游官方站的,没有任何本地兜底分支,也没有任何位置可以存放本地元数据。自研内容走这条通道会在**第一次元数据请求时就失败**,而且这不是"加个判断绕过去"的问题,是"本地仓库"这个概念在那条通道上完全不存在,需要从零建一套。
>
> 而 HF 兼容通道**已经具备**脱离上游、纯读本地内容对外服务的完整能力。本功能所谓"复用现有缓存方案",复用的正是这一套。

> **特别提示**:本文档所说的"数据集",指的是 **HF 兼容通道下的数据集类型**,不是 ModelScope 通道的数据集。两者路由不同、存储不同,不要混淆。仓库中存在 ModelScope 相关的代码和缓存目录,看到"数据集"字样时请先确认自己在哪条通道上。

### 3.1.2 【硬性约束】允许改什么、不允许改什么

| 层次 | 本功能的要求 |
|---|---|
| 元数据解析层(把版本标签解析成快照标识、查询文件信息) | **允许**为本地仓库增加分支,使其不去上游求证、直接使用本地数据 |
| 文件内容读取与传输链路(含分段响应、缓存文件读取) | **必须原样复用**,不允许新建、不允许分叉出一条自研内容专用的传输路径 |
| 现有公开模型的任何对外行为 | **不允许改变** |

### 3.1.3 【硬性约束】本期仅支持单节点部署

- 本功能**仅在单节点(standalone)部署下受支持**。
- 上传产生的内容与元数据只存在于**执行上传的那个节点**上。
- 集群部署时,自研仓库的下载请求**必须被固定路由到上传节点**,这是使用方的部署责任,需写入交付文档的已知限制。

**【明确不做】**:不做跨节点的元数据同步、文件复制、路由亲和或权威节点机制。这些会让工作量成倍增长,不属于本期。

### 3.2 【明确不做】—— 防止过度设计

以下内容**本期一律不实现**。如果你认为其中某项是必需的,请**先提出来确认,不要自行实现**。

| 不做的事 | 原因 |
|---|---|
| 兼容上游站点的官方上传协议 | 该协议非常重,且依赖完整的版本控制后端,而本系统没有。上传方是我们自己的团队和 CI,没有兼容必要 |
| 引入版本控制系统作为后端 | 同上。见 FR-5:快照标识只是一个由内容算出来的字符串,不是版本控制 |
| 分支管理:创建分支、合并、历史记录、回滚、版本对比 | 本期只需要"能上传、能按标签取到最新" |
| 跨节点同步 / 集群支持 | 见 §3.1.3 |
| 专用上传客户端 / CLI / SDK | 本期用通用 HTTP 工具(curl)直接调用即可,见 §4 |
| 整目录批量上传、多文件并行编排 | 本期是单文件接口。批量由调用方用脚本循环调用实现 |
| 分片并行上传、乱序分片、分片重组 | 本期续传只支持**从当前可续传位置顺序往后传**(见 FR-4) |
| Web 上传界面 / 管理后台 | 本期是接口能力,调用方是脚本和 CI |
| 用户注册体系、角色权限模型(RBAC)、多租户、配额管理 | 本期身份校验只需要"是否是被授权的上传方"这一个判断 |
| 业务层的文件大小限额、存储容量管理 | 不在本功能职责范围内。但**格式能力上限的拒绝**与**无界写入防护**是本功能的责任,见 FR-2 |
| 精细的垃圾回收策略、残留容量统计与配额 | 能识别、能清理、不无限增长即可 |
| 为清单维护建增量索引 / 数据库 | 见 FR-3 的性能要求,先给出规模指标,不达标再谈优化 |
| 模型文件格式的深度校验、病毒扫描 | 上传方是内部可信团队,成本高收益低 |
| 存储层的去重、压缩、加密 | 与本功能目标无关 |
| 上传限速、优先级调度、流量整形 | 无实测瓶颈之前不做 |
| 引入新的外部依赖(数据库、对象存储、消息队列等) | 本功能不应该扩大系统的部署复杂度 |

### 3.3 本期不做但需要预留可能性

以下三项**本期不实现**,但落盘方式和接口形态不应该让将来实现它们变得不可能:

- **删除/下线已上传的仓库版本**。
- **上传审批流**。
- **分块上传(按服务端缺失的块乱序/并行上传)** —— 见 3.3.1。

#### 3.3.1 分块上传的前向兼容要求

**本期明确不做分块上传**,但必须保证将来能低成本加上。

**为什么现在不做**:上传接口只监听本机回环(§4.1),没有真实网络传输环节,分块并行优化的是网络,在这里几乎没有收益,反而会让多个分块并发争用同一个文件。同时它会把协议复杂度翻倍(缺失块查询、块对齐、边缘半块处理、单文件内并发),与"一条 curl 完成上传"的设计目标直接冲突。**触发重新评估的条件是:上传接口改为支持远程接入。**

**为什么将来能低成本加上**:底层缓存格式是**按块随机寻址**的,块的就绪状态用位图记录,不要求连续;下载侧本来就是逐块判断"这块有没有"。因此"必须顺序、必须连续"纯粹是本期在**协议层自己加的约束**,不是存储层的限制。将来放宽它不需要改存储、不需要数据迁移,顺序上传的行为是分块协议的一个子集,向后兼容。

**【硬性约束】本期不得做的两件事**(做了就会堵死上述迁移路径):

1. **不得使用"边接收边累加"的流式摘要计算**。摘要必须在文件完整之后,**把落盘内容整个读一遍重新计算**。
   > 这不只是为了将来 —— 本期就必须这样做:续传可能跨进程重启,流式哈希的中间状态届时已经丢失,而我们又禁止把它存到外部状态里(FR-4.6.5)。换句话说,**唯一正确的做法恰好也是唯一可扩展的做法**。不要为了省这一次读盘去引入流式哈希。
2. **写入路径不得做成"只能追加"的形式**。必须复用现有的按块写入能力,保持"能写任意位置的块"这一特性。

**【明确不做】**:不要现在就实现缺失块查询、块对齐协商、分块并发控制。保持上述两条即可,不需要为将来预留任何接口字段。

## 4. 接口形态与网络边界

> 本节约定**调用方式的形态与暴露范围**,不指定具体路径、参数名和响应结构 —— 那些由实现者设计,但需在交付文档中写清。

### 4.1 【硬性约束】网络暴露边界

**上传相关的接口(含上传与进度查询)只允许监听本机回环地址(`127.0.0.1`),不得对外暴露。**

- 对外的下载服务保持现状不变,监听地址照旧。
- 上传接口与下载服务**分开监听**:即使下载服务绑定在对外地址上,上传接口也只能从本机访问到。
- 上传凭证仍通过请求头传递(见 FR-1)。由于只走本机回环,明文传输的风险被限制在本机内。

> **为什么这是硬性要求**:当前服务默认监听全部网络接口。如果上传接口注册到同一个对外监听上,那么"文档里写了只用 localhost 调用"**不构成任何安全保障** —— 其他机器照样能访问,而且共享凭证是明文传输的。安全边界必须由监听地址来保证,不能靠约定。

**副作用(需写入交付文档)**:上传方必须在服务器本机操作,或自行建立端口转发/跳板。这是有意为之的限制。

**【明确不做】**:不做 TLS、不做网关、不做跨域、不做远程接入相关的任何设计。

### 4.2 调用形态

> **环 1 已定稿接口**:当前完整上传接口为 `POST /api/local-upload/:repoType/:org/:repo/:revision/*?size=<完整字节数>&sha256=<完整内容SHA-256>`,文件内容放在请求体中,上传凭证请求头为 `X-Dingo-Upload-Token`。其中 `*` 是仓库内文件路径,支持 `subdir/config.json` 这类多级路径。成功响应必须包含本次生效后的快照标识(`commit`)。后续环新增字段或接口时,应保持一条 curl 完成完整上传的使用形态不被破坏。
>
> **环 2 新增**:查询参数 `overwrite=true` 用于显式声明覆盖(见 FR-7)。成功响应新增 `blobReused` 字段,为 `true` 表示本次走了幂等/去重快路径、未重复写入内容(对应 §9.8 中"需能观测到走了快路径"的要求)。

1. **用通用 HTTP 工具(如 curl)就能调用**,不需要任何专用客户端。这是接口设计的硬性检验标准:
   - 一次**完整上传**必须能用**一条 curl 命令**完成;
   - 一次**续传**必须能用**两条 curl 命令**完成(先查进度,再从该位置继续传)。
   - 超出这个复杂度,说明接口设计跑偏了。
2. **一次调用上传一个文件**,调用方需要能指定:
   - 仓库类型(模型 / 数据集)
   - 组织名与仓库名
   - 版本标签
   - 该文件在仓库内的相对路径(可以是多级目录,如 `subdir/config.json`)
   - 该文件的**完整字节大小**(必填)
   - 该文件的**完整内容 SHA-256 摘要**(必填,见 FR-2)
   - **本次请求体从该文件的哪个字节位置开始**(用于续传)。**声明与不声明是两种不同的语义,不是"不声明等于声明 0"**:
     - **不声明** = "我传的是完整文件"。服务端从 0 全量写入,覆盖此前可能残留的未完成内容,末尾由整体摘要校验兜底。这条路径**不受 6.4.4 起始位置校验的约束**,因为全量覆盖写入结构上不可能产生拼接(坑 10)。这是"一条 curl 完成完整上传"得以成立的前提。
     - **显式声明** = 续传。必须严格等于服务端的可续传偏移量,见 6.4.4。
   - 文件内容(本次要传的那一段)
3. 需要提供一个**进度查询能力**。调用方给出与上传相同的定位信息(仓库类型、组织名、仓库名、版本标签、仓库内路径)**以及该文件的完整摘要**,即可得知:
   - 该文件此前已绑定的**完整大小**
   - 该文件此前已绑定的**完整摘要**
   - **当前可续传偏移量**(定义见 FR-4)
   - 该文件**是否已经生效**(用于区分"从没传过"与"早就传完了",两者的可续传偏移都不是一个进行中的值)

   > **为什么摘要是查询的入参而不只是返回值**:未完成内容的存放位置由摘要决定(与已生效内容同属一个内容寻址空间),而"某个路径当前正在传的是哪个摘要"这一映射只存在于进行中的上传里。若要让服务端仅凭路径就答出摘要,就必须额外维护一份路径到摘要的状态,那正是 6.4.5 明令禁止的。调用方本来就必须知道摘要(上传时是必填项),把它作为入参不增加任何使用负担。
4. 上传凭证通过**请求头**传递。
5. 其余参数通过 URL 路径或查询参数传递,文件内容通过请求体传递。

**结果反馈要求**:调用返回时,调用方必须能明确知道成功还是失败,失败时能知道**是哪一类失败**(见 FR-8)。上传成功返回时,还应当能区分"这一段收下了,但文件还没传完"和"文件已完整生效"。不允许出现"返回成功但实际没生效"的情况。

## 5. 使用场景

### 场景 A:算法工程师发布一个新训练出来的模型

1. 工程师手上有一个目录,里面是训练产出的若干文件。
2. 他在服务器本机用一个简单脚本循环调用上传接口,逐个把文件传上去。每个文件需要先算出 SHA-256 和大小随请求带上。
3. 每传完一个文件,他都能得到明确的成功/失败反馈。
4. 全部传完后,这个仓库版本可以被正常下载。

### 场景 B:内部用户使用这个模型

1. 用户使用**和拉取公开模型完全一样的工具和命令**,只是把仓库名换成自研模型的仓库名。
2. 能够拉取整个仓库,也能够只拉取其中某一个文件。
3. 用户**感知不到**这个模型和公开模型有任何区别。

### 场景 C:模型被重新训练,需要更新

1. 工程师用**相同的仓库名**、**新的版本标签**再传一次。老版本仍然可用,新版本可用。
2. 若要用相同版本标签重传,默认会被拒绝,需要显式声明覆盖(见 FR-7)。
3. 无论是新增文件还是覆盖文件,**只要该版本的内容变了,快照标识就必须变**,已经拉取过的用户能拿到新内容(见 FR-5)。

### 场景 D:大文件上传中途失败,接着传

1. 一个 30GB 的权重文件传到 18GB 左右时,网络断开 / 进程被杀掉。
2. 此时下载方**不应该**能拉到这个半成品文件。
3. 工程师重新执行上传脚本。脚本先向服务端**问一句"这个文件的可续传位置在哪"**,得到一个偏移量。
4. 脚本从本地文件的该偏移处开始,带上**同一个大小和同一个摘要**,把剩下的部分传上去。
5. 全部收完后服务端重算整文件摘要并比对,通过则整体生效。
6. 若中途又断,重复第 3~5 步即可,可以断多次。

### 场景 E:上传数据集

与场景 A 相同,只是仓库类型指定为数据集。行为要求完全一致。

## 6. 功能需求

### FR-1 上传者身份校验 【硬性约束】

**要求**:上传接口必须校验调用方身份,未通过校验的请求一律拒绝,且不产生任何落盘副作用。

**本期采用最简方案**:
- 服务端通过**配置**持有一个共享上传凭证(单一凭证,所有上传方共用)。
- 调用方通过**请求头**携带该凭证。
- 若服务端未配置该凭证,上传接口应当**默认关闭**(拒绝所有上传),而不是默认放行。
- 拒绝时返回明确的、可区分的失败信息:"未提供凭证" 与 "凭证无效" 应该能区分。

**【明确不做】**:不做多凭证、不做按人区分、不做多角色、不做按仓库粒度的授权、不做凭证的在线签发与轮转。

---

### FR-2 上传内容合法性校验 【硬性约束】

#### 6.2.1 完整摘要是必填项 🔴

**要求**:调用方**必须**在每次上传请求中声明该文件的**完整内容 SHA-256** 和**完整字节大小**。缺少任一项的请求一律拒绝。

**服务端行为**:
1. 首次上传某个文件时,把声明的大小与摘要**绑定**到该文件上。
2. 后续对同一文件的每次续传请求,必须携带**完全相同**的大小与摘要,不一致则拒绝(见 FR-4)。
3. 文件完整接收后,服务端**对整个文件重新计算 SHA-256**,与绑定值比对。**不一致则该文件不生效**。

> **为什么摘要必须是必填,而不是"提供了才校验"**:有两个独立的理由,任一个都足以决定这件事。
>
> **理由一(功能性)**:自研内容的存放位置是**由内容摘要决定的** —— 摘要就是存放路径的一部分。服务端在写入第一个字节之前就必须知道往哪里写,而摘要要等内容全部收完才算得出来。这是个先有鸡还是先有蛋的问题,唯一的解法就是**让调用方先告诉服务端**。
>
> **理由二(正确性)**:如果摘要可选,服务端在文件收完时只能算出"拼接结果的摘要",却没有任何期望值可以比对。那么"A 文件的前半段 + B 文件的后半段"会被当成一个完全合法的新文件收下,产生静默的坏数据(见 §7 坑 10)。

**【明确不做】**:不做多种摘要算法可选、不做分段摘要校验(见 FR-4)。

#### 6.2.2 其他必须校验的项

| 校验项 | 说明 | 违反时 |
|---|---|---|
| **路径安全** | 见 6.2.3 | 拒绝,记录告警 |
| **仓库命名空间** | 只允许写入约定的"本地仓库"命名空间(见 FR-5) | 拒绝 |
| **仓库类型** | 只允许模型与数据集两种合法类型 | 拒绝 |
| **格式能力上限** | 见 6.2.4 | 拒绝 |

#### 6.2.3 路径安全 【硬性约束】

**要求**:凡是**最终会参与磁盘路径拼接**的输入,都必须校验,不能只校验"文件在仓库内的相对路径"。至少包括:组织名、仓库名、版本标签、快照标识、文件摘要、仓库内文件路径。

**必须拒绝的形式**(每一项都要覆盖,不能只挡最直白的那一种):

- 向上跳转(`..` 及其各种变形)
- 绝对路径
- 正斜杠与反斜杠(在不该出现的字段中)
- 盘符前缀
- NUL 及其他控制字符
- 路径中间环节指向仓库目录之外的符号链接

**判定标准**:任何输入组合,最终写入位置都必须落在该仓库的目录范围之内。

> **为什么路径安全是不可妥协的**:这个接口的能力本质是"把调用方给的字节写到服务器的指定位置"。这天然带有风险。这个风险不通过"不做这个功能"来规避,而是通过**把"指定位置"严格限制死**来规避。

#### 6.2.4 大小限制与无界写入防护 【硬性约束】

**本功能不设业务层的文件大小上限**(容量与磁盘防护由服务器运维手段负责)。**但"不设业务上限"不等于"没有上限"**:

| 防护项 | 要求 |
|---|---|
| **格式能力上限** | 底层缓存格式对单文件大小有硬上限(由可记录的块数量与块大小共同决定,当前配置下约为 8 TiB)。声明大小超过该上限的请求**必须被拒绝**,并给出明确原因。同样地,超过 `int64` 表示范围、超过可用磁盘或文件系统能力的声明也必须拒绝 |
| **必须声明大小** | 未声明完整大小的请求一律拒绝,不接受长度未知的流式写入 |
| **实际与声明必须一致** | 写入时必须比对实际接收的字节数。超出声明值时**立即中止写入并拒绝**,不允许继续接收 |
| **残留可回收** | 未完成的上传会留下部分内容(断点续传所必需),但必须有**保留期限**(可配置)。超期未被续传的残留可被回收,不能随失败次数无限累积 |
| **并发上限** | 同时进行的上传数量应有一个上限(可配置,默认取一个保守的小数值)。超过时明确拒绝 |

> **"必须声明大小"是防止无限上传最有效的手段**:没有它,一个不断发送数据的连接可以把磁盘写满,而服务端无从判断何时该停。

> **这里有一处需要权衡**:断点续传要求**保留**未完成的部分内容,而残留回收要求**清理** —— 两者是同一份数据。用保留期限化解:期限内保留以支持续传,超期视为已放弃、可回收。期限取一个明显大于正常上传耗时的值即可(例如按天计),不必精细。

#### 6.2.5 重复上传防护

| 情况 | 要求 |
|---|---|
| 同一位置、摘要完全相同的文件再次上传 | 识别出来,直接返回成功,**不重复写入**。这是幂等快路径 |
| 同一位置、摘要不同的文件再次上传 | 默认拒绝(见 FR-7) |

**【明确不做】**:不做跨仓库的内容去重,不做全局内容索引。

### FR-3 生效语义与清单维护 【硬性约束】

#### 6.3.1 单个文件的生效

1. 文件在**完整接收、摘要校验通过之前**,对下载方不可见。半成品不得被当作正常数据服务出去。
2. 一次上传要么完全成功(文件可下载、清单已更新、快照标识已更新),要么完全没发生。
3. 中断不得损坏该版本中**已经生效的其他文件**。

#### 6.3.2 清单必须重建为完整清单

每次有文件生效时,必须**重建该仓库版本的完整文件清单**,清单要包含这个版本下**此前已生效的全部文件**,而不只是本次上传的这一个。清单必须与实际落盘文件**一一对应**。

> **为什么**:见 §7 坑 3。整仓下载依赖这份清单。逐个文件上传时,如果每次只把当前文件写进清单,清单就会只剩最后一个文件,整仓下载就废了。

**性能要求**:实现者需要给出**本期支持的单仓库最大文件数**,并在 **1000 个文件**的规模下验证逐个上传的总耗时可接受。

**【明确不做】**:不要为此建增量索引或引入数据库。先给出规模指标,不达标再谈优化。

#### 6.3.3 崩溃一致性

**要求**:一次文件生效涉及多个磁盘对象(文件内容、链接、文件信息、版本清单)。进程在任意时刻崩溃,重启后系统看到的状态必须是**合法的**:要么是这次上传之前的状态,要么是这次上传完成后的状态。

**不允许出现的状态**:半截的元数据、空的元数据文件、清单里有但文件不存在、文件存在但快照标识没更新。

**降低要求的说明**:本期**不要求**做完整的崩溃注入测试矩阵,只要求最终那一步"让内容对外可见"的动作是原子的,且异常状态可被识别。

**【明确不做】**:不做事务日志、不做两阶段提交、不引入任何一致性中间件。

---

### FR-4 大文件与断点续传 【硬性约束】

#### 6.4.1 大文件处理

1. 支持单个大文件的上传(GB 量级,上限见 6.2.4)。
2. 服务端**内存占用与被上传文件的大小无关**。不允许出现"整个文件读进内存"这类实现。
3. 上传中断不得损坏该版本中已生效的其他数据。

#### 6.4.2 可续传偏移量的定义 🔴

**"可续传偏移量"必须定义为:服务端已经持久化的、连续的、可以从此处安全接着写的字节位置。**

**它不是"网络上已经收到了多少字节"。** 这两个值在中断时通常不相等。

> **为什么必须这样定义**:底层缓存格式是**按块**记录"这部分已就绪"的。如果中断发生在某个块的中间,那半个块**不算已就绪**,可续传位置会退回到这个块的开头。因此调用方最多需要重传一个块的数据量,这是**正常且预期的行为**,不是 bug。
>
> 如果错误地把"收到的字节数"当作进度返回,续传就会从一个服务端并未真正持久化的位置接着写,直接造成数据错位。

**要求**:进度查询返回的必须是这个持久化偏移量,且它必须**从现有缓存文件形态本身推导出来**。

#### 6.4.3 续传流程

1. 调用方查询进度,得到已绑定的完整大小、已绑定的摘要、可续传偏移量。
2. 调用方从本地文件的该偏移处开始,带上**同一个大小和同一个摘要**,把剩余部分作为请求体发上来,并声明本次请求体的起始位置。
3. 服务端把这段内容接在已有内容之后。
4. 累计接收达到声明的完整大小后,**对整个文件重新计算摘要**并与绑定值比对,通过才整体生效。

#### 6.4.4 续传的前提校验 【硬性约束】

接受一次续传请求前,必须确认它续的确实是**同一个文件**。以下任一情况都必须**拒绝**,而不是接着写:

| 情况 | 处理 |
|---|---|
| 本次声明的完整大小与已绑定值不一致 | 拒绝 |
| 本次声明的完整摘要与已绑定值不一致 | 拒绝 |
| 本次声明的起始位置**不等于**服务端的可续传偏移量 | 拒绝,并在错误信息中**告知实际的可续传偏移量**,让调用方据此重试 |

> 起始位置**必须严格相等**:小于会造成重复写入/覆盖,大于会留下空洞。两种都必须拒绝,**不要试图容错处理** —— 在这里容错等于制造坏数据。

**本节只约束续传请求**,即显式声明了起始位置的请求。**未声明起始位置的完整上传不在此列**(见 §4.2 第 2 条):它从 0 全量覆盖写入,不读取也不比对可续传偏移量,正确性由末尾的整体摘要校验保证。

> **为什么这样划分不会放过坑 10**:坑 10 的本质是"把一段内容接到另一段后面"时接错了。全量覆盖写入没有"接"这个动作 —— 每一个块都被本次请求写过,残留内容不可能有任何一部分幸存到最终结果里。真正的兜底始终是"收完之后对整个文件重算摘要",这一点两条路径完全一致。

**一个必须处理的边界**:若已存在的未完成内容记录的完整大小与本次声明的不一致(同一摘要却声明了不同大小,说明至少有一方是错的),该未完成内容对本次请求不可复用,必须丢弃后重新开始,而不是试图在其上继续写。

#### 6.4.5 进度状态的来源 【硬性约束】

**【明确不做】不要另建一套进度状态存储**:不要建表、不要写额外的状态/进度文件、不要在内存里维护上传会话表。

> **理由**:一是重复造轮子(现有缓存格式已经记录了"哪些部分已就绪",下载侧的续传就是靠它);二是独立状态与实际落盘内容之间必然出现不一致(比如进程崩溃在"写完数据"和"更新状态"之间),那种不一致会直接导致数据损坏且极难排查。

#### 6.4.6 范围限制

- 只支持**从当前可续传位置顺序往后续传**。不支持乱序分片、不支持并行分片、不支持覆盖已接收区间。
- **摘要只在文件完整之后对整个文件校验一次**,不做分段校验。分段校验拦不住拼接问题(每段单独看都是"完好"的)。
- 不要试图兼容上游站点下载接口的分段请求语义(Range)。那是**下载方向**的概念。上传方向的"从哪里继续"是本功能自己的参数,两者不要混用同一套语义。

---

### FR-5 命名空间、版本标签与快照标识 【硬性约束】

#### 6.5.1 命名空间

**自研内容一律使用保留组织名 `dingo-local`。**

- 仓库形如 `dingo-local/<仓库名>`,模型与数据集共用这一个保留组织名。
- 上传接口**只接受组织名等于 `dingo-local` 的请求**,其他一律拒绝。
- 该值应当是一个**配置项**,默认值为 `dingo-local`。修改配置不负责迁移已有数据。

> **为什么需要独立命名空间**:三个原因。一是防止自研内容和上游真实存在的同名仓库互相覆盖;二是系统需要一个简单可靠的判据来识别"这个仓库是本地的,不要去上游找它"(见 §7 坑 1);三是磁盘清理需要据此把自研内容排除在淘汰之外(见 FR-9)。三件事用同一个机制一次解决。

**【明确不做】**:不做多级命名空间、不做按团队划分的子组织。

#### 6.5.2 版本标签与快照标识必须分离 🔴

现有下载链路的工作方式是:**先把版本标签解析成一个快照标识,再用快照标识去定位文件**,并把快照标识回给客户端。而标准下载客户端**普遍假设"快照标识不变 = 内容不变"**,会直接复用本地已缓存的内容。

因此本功能必须区分两个概念:

| 概念 | 性质 | 要求 |
|---|---|---|
| **版本标签(revision)** | **可变**,由调用方指定,如 `main`、`v1` | 必须支持默认值 `main`。同一仓库可有多个标签共存 |
| **快照标识(commit)** | **不可变**,由服务端生成 | **建议由该版本的完整文件清单确定性计算得出**(内容相同则标识相同) |

**行为要求**:
1. 版本标签**原子地指向**当前最新的快照标识。
2. **只要该版本的内容发生了变化,就必须产生一个新的快照标识** —— 新增文件算变化,覆盖文件也算变化。
3. 下载响应中回给客户端的快照标识,必须是**变化后的新标识**。

> **为什么这条必须做,以及它为什么不是"引入版本控制"**:
>
> 我们是**逐个文件上传**的。传完第 1 个文件时该版本有 1 个文件,传完第 2 个时有 2 个 —— **版本内容一直在变**。如果快照标识始终等于版本标签(比如恒为 `main`),那么已经拉取过的客户端会认为自己手上的就是最新的,**永远看不到后面上传的文件**。同样地,覆盖重传后用户也拿不到新内容。
>
> 这不需要引入 Git、不需要历史记录、不需要回滚。它只需要"**用清单算一个确定性的字符串**"—— 而清单本来就是 FR-3 要求维护的东西。工作量增量很小,但不做就会坏。

**【明确不做】**:不做版本历史、不做回滚、不做快照之间的差异对比、不做分支、不做 `latest` 这类动态别名、不做语义化版本解析。

---

### FR-6 上传后必须能被正常下载 【硬性约束 —— 核心验收项】

**要求**:上传完成后,自研内容在下载侧的表现必须与从上游下载缓存下来的内容**完全一致**。以下每一项都必须成立(模型与数据集两种类型都要成立):

| 能力 | 要求 |
|---|---|
| 整仓拉取 | 用标准客户端拉取整个仓库,能拿到该版本的**全部**文件,一个不少 |
| 单文件拉取 | 能单独拉取仓库中的某一个文件 |
| 多级目录 | 仓库内带子目录的文件能被正确拉取,目录结构保持 |
| 分段下载 | 支持按字节区间请求文件的一部分,返回内容正确 |
| 客户端断点续传 | 下载方中断后重连能继续 |
| 文件元信息 | 文件大小、内容标识等信息正确,客户端的完整性校验能通过 |
| 版本解析 | 按指定的版本标签能取到对应内容,且拿到的快照标识正确 |

**【硬性约束】**:上述能力必须通过**复用现有下载链路**获得(边界见 §3.1.2),不允许为自研内容另建一条内容传输通道。

**判定标准(实现者可用于自检)**:落盘之后,**仅看磁盘上的产物,应当无法区分它是上传来的还是从上游下载来的**。如果能区分,说明落盘形态不对。

---

### FR-7 覆盖与并发

#### 6.7.1 覆盖策略

| 情况 | 行为 |
|---|---|
| 目标位置不存在该文件 | 正常写入 |
| 已存在,且摘要完全相同 | 直接返回成功,不重复写入 |
| 已存在,摘要不同,**未显式声明覆盖** | **拒绝**,并明确告知"已存在,如需覆盖请显式声明" |
| 已存在,摘要不同,**显式声明覆盖** | 允许覆盖。覆盖后清单、文件信息、**快照标识**全部同步更新 |

**向已存在的版本追加新文件是允许的**,不算覆盖,但**同样会产生新的快照标识**。

#### 6.7.2 并发

1. 同一个仓库、同一个版本、同一个文件路径,同一时刻只允许一个上传在进行。第二个请求应当被**明确拒绝并告知原因**,而不是排队或与之交错。**续传请求同样受此约束**。
2. 不同文件、不同仓库之间的上传互不影响,可以并行(受 FR-2 的并发上限约束)。
3. 上传过程中,该仓库版本中**其他已生效文件的下载不受影响**。
4. 进度查询是只读操作,不受上述互斥约束。
5. **清单与快照标识的更新必须是安全的**:两个不同文件并发上传时,最终清单必须同时包含两者,快照标识必须反映最终内容。

---

### FR-8 可观测性与错误反馈

1. 上传的开始、完成、失败与原因都要有日志。路径逃逸、凭证失败这类安全相关事件要能在日志中被识别出来。
2. 失败信息必须能让调用方**自行判断问题归属**。以下几类必须能区分:
   - 凭证问题(未提供 / 无效)
   - 参数问题(命名空间不对 / 类型不对 / 路径非法 / 未声明大小或摘要 / 超过格式能力上限)
   - 内容问题(实际大小与声明不符 / 完整摘要校验失败)
   - 续传问题(大小或摘要与绑定值不符 / 起始位置不等于可续传偏移 —— 需回传实际偏移量)
   - 冲突问题(已存在需显式覆盖 / 同一文件正在上传中 / 超出并发上限)
   - 服务端故障
3. **【明确不做】**:不做上传专用的监控面板、不做告警规则、不引入新的指标体系。

---

### FR-9 自研内容不得被磁盘清理淘汰 【硬性约束】

**要求**:`dingo-local` 命名空间下的内容属于**持久发布源**,必须被排除在现有的缓存淘汰机制之外。

> **为什么这是硬性要求**:现有的磁盘清理任务在缓存超限时,会按"最久未访问 / 最早修改 / 体积最大"等策略**直接删除缓存文件**,且没有任何白名单。
>
> 对公开模型来说这没问题 —— 删掉了还能从上游重新下载。但**自研模型删掉就永远没有了**,而它可能是我们唯一的发布源。这是数据丢失级别的风险。
>
> 更糟的是,现有清理只删文件、**不删元数据**。结果会是"版本信息和文件清单都还在,但实际内容没了"这种破损状态,对外表现成难以排查的下载失败。

**【明确不做】**:不要为自研内容单独实现一套淘汰策略、不要做容量配额。把它排除在淘汰之外即可,容量问题由运维手段解决。

---

## 7. 已知风险与踩坑点

> 以下每一条都来自对现有系统的实际调研,是**已经确认存在**的陷阱,不是假想风险。
> 每条按 **是什么 / 怎么来的 / 解决方向** 说明。解决方向只给方向,具体做法由实现者决定。

---

### 坑 1:上传成功了,但下载时报"找不到" 🔴

**是什么**
上传明明成功了,文件确实在服务器磁盘上,但用户去下载时返回"资源不存在"。这个问题**在某些部署配置下出现、另一些配置下不出现**,极易在测试环境漏测、到生产才爆炸。

**怎么来的**
现有系统的设计前提是:**所有仓库都源自上游站点**。当服务运行在"在线"模式下,处理下载请求时会**先向上游求证**这个仓库和版本是否存在,然后才会去读本地缓存。自研内容在上游根本不存在,求证必然失败,请求在走到"读本地缓存"之前就被中断了。

而在"离线"模式下,系统不去上游求证,直接读本地,所以看起来是好的 —— 这就是为什么它会漏测。

**解决方向**
识别"这是一个本地仓库"(依据就是保留组织名 `dingo-local`),对本地仓库**跳过向上游求证,直接使用本地数据**。

- 这个识别需要作用在**所有**会触发"向上游求证"的入口上,不能只改一处。实现者需要自行排查完整。
- 【明确不做】不要引入"先查上游失败再降级查本地"的兜底策略 —— 那会让每次下载自研内容都多一次注定失败的外网请求,既慢又脆弱。

**验收**:同一套下载用例,在**在线模式和离线模式下都必须通过**,行为一致。

---

### 坑 2:把文件直接拷贝到缓存目录,下载时内容错乱

**是什么**
实现者最容易的第一反应是"把上传的文件复制到缓存目录对应位置就行了"。结果是下载失败,或者下载到的内容是乱的。

**怎么来的**
现有的缓存文件**不是原始文件的副本**。它是一种带内部结构的自定义格式,除了内容本身,还包含头部信息和"文件的哪些部分已经就绪"的记录。下载侧完全按这个结构去读。

**解决方向**
上传落盘必须**复用系统现有的缓存写入方式**,产出与"从上游下载完成之后"完全一致的文件形态,包括"全部内容均已就绪"这一状态的正确标记。

上传和下载的差别只在于**内容从哪里来**,内容**写到哪里去、怎么写**应该是同一套东西。

---

### 坑 3:单个文件能下载,但整仓拉取只有最后传的那一个 🔴

**是什么**
逐个上传了 10 个文件,单独按文件名下载每个都没问题,但"拉取整个仓库"时只拿到最后上传的那 1 个。

**怎么来的**
"整仓拉取"不是靠扫描目录实现的,它依赖一份**该版本包含哪些文件的清单**。这份清单在正常流程里是从上游拿到的;自研内容没有上游,清单必须由上传功能自己生成。而本期是单文件接口 —— 如果每次上传都用"本次这一个文件"去覆盖清单,清单就永远只有一个文件。

**解决方向**
每次文件生效时,**重建该版本的完整清单**(见 FR-3)。

**验收**:必须用"逐个上传多个文件后整仓拉取"的用例验证,单文件上传+单文件下载的用例**测不出这个问题**。

---

### 坑 4:客户端报完整性校验失败,或者反复重新下载

**是什么**
下载能开始,但客户端最后报校验不通过;或者客户端每次都认为本地缓存无效,反复重下同一个文件。

**怎么来的**
系统使用**内容标识**作为缓存文件的存放依据和完整性校验依据。下载客户端也会用它来判断本地副本是否有效。如果上传时记录的标识和实际内容对不上,这条链路就会崩。

**补充背景**:项目近期刚修复过一次与"下载中断、完整性校验失败"相关的问题,说明这条链路对标识的正确性非常敏感。

**解决方向**
- 标识必须由服务端依据实际落盘内容计算,调用方声明的值用于**绑定与比对**,但最终以服务端重算的结果为准(见 FR-2)。
- 同一份内容无论上传多少次,得到的标识必须相同。
- 标识的计算方式需要与下载侧的使用方式保持一致 —— 先确认现有体系里这个标识是怎么产生和怎么被消费的,再决定上传侧怎么算。**不要凭直觉选一种哈希就用**。

---

### 坑 5:被"版本/分支"带偏,做出一个版本控制系统

**是什么**
看到"版本""快照标识"这些词,容易联想到要实现分支、合并、历史、回滚。这会让工作量膨胀一个数量级。

**怎么来的**
上游站点的版本标识背后确实是一套完整的版本控制系统。但本系统不需要有。

**解决方向**
- 版本标签 = 一个可变的字符串标签。
- 快照标识 = **由文件清单算出来的一个确定性字符串**,仅此而已(见 FR-5)。
- 明确不做:分支、合并、历史、回滚、差异对比、标签别名。

---

### 坑 6:自研内容和公开内容撞名

**是什么**
自研模型取了和上游某个真实模型相同的名字,导致数据互相覆盖或混淆。

**怎么来的**
自研内容和缓存下来的公开内容**共用同一套存储位置和命名规则**。

**解决方向**
见 FR-5:强制使用保留组织名 `dingo-local`,且上传接口拒绝写入该命名空间之外的位置。

---

### 坑 7:用户拉到了半成品文件

**是什么**
一个 30GB 的文件正在上传,传到一半时用户去拉取,拿到了不完整的文件。

**怎么来的**
上传耗时长。如果落盘位置就是对外服务的位置,中间态天然可见。

**解决方向**
见 FR-3:完整接收且摘要校验通过之前不可见。

> **注意**:这条只解决**单个文件**的半成品问题。"整个仓库还没传完就被用户看到"是另一回事,见 §11 已知限制。

---

### 坑 8:并发上传把数据搅乱

**是什么**
两个人同时上传同一个文件,或者脚本被重复执行,导致内容混杂、清单错乱。

**怎么来的**
上传是长时操作,天然存在重叠窗口。而清单和快照标识是"每次上传时重建"的,**它们本身也是并发争用点** —— 两个不同文件同时上传,可能各自基于旧清单重建,导致其中一个的记录丢失。

**解决方向**
- 同一文件的并发上传互斥,冲突时**明确拒绝**,不做排队等待。
- 清单与快照标识的更新必须是安全的:两个不同文件并发上传时,最终结果必须同时包含两者。这一点容易被漏掉,需要专门验证。

---

### 坑 9:选错了下载通道,整个方案报废

**是什么**
把上传内容落到了 ModelScope 通道的缓存目录下。内容确实写进磁盘了,但无论怎么请求都拿不到,而且怎么改都改不通。

**怎么来的**
服务器上并存两条独立的下载通道(见 §3.1.1),缓存位置、文件形态、元数据机制**完全不同**。仓库中存在名字里带 ModelScope 的缓存目录和一整套处理逻辑,很容易被误认为是标准存放位置。尤其本期需求包含"支持数据集",而 ModelScope 通道里也有数据集处理,极易一头扎进去。

而 ModelScope 通道是**纯转发代理**,自研内容在那条通道上是**结构性地不可能**被服务出去的。

**解决方向**
动手前先确认自己在哪条通道上。判断依据:**这条通道在没有外网的情况下,能不能只靠本地文件把内容服务出去?** 能的那条才是目标。

---

### 坑 10:续传把两个不同文件的内容拼在了一起 🔴

**是什么**
文件下载下来能用、大小也对,但内容是坏的 —— 前半段来自 A 文件,后半段来自 B 文件;或者文件中间有一段是空的。这类损坏**不会在上传时报错**,往往要到用户加载模型失败时才暴露。

**怎么来的**
断点续传的本质是"把这段内容接到已有内容后面"。服务端如果不加确认就接受,以下情况都会静默产生坏数据:

- 工程师改了模型重新训练,用**同一个文件名**续传,新文件的后半段被接到了旧文件的前半段上;
- 声明的起始位置**小于**可续传偏移 → 内容重叠覆盖;
- 声明的起始位置**大于**可续传偏移 → 中间留下没写过的空洞;
- 只对每一段分别做了校验,没有对整个文件做校验 —— 每段单独看都"完好",拼起来却是错的。

**解决方向**
- **强制声明完整摘要**,并在文件收完后对整个文件重算比对(见 FR-2)。这是拦住上述所有情况的最后一道关口,**不能省**。
- 续传前确认是同一个文件:大小与摘要必须与绑定值一致。
- 起始位置必须**严格等于**可续传偏移量,大于小于都拒绝,并把实际值告诉调用方。**不要做容错**。

**验收**:必须专门构造"续传时换了个文件"、"起始位置报错"这两类用例。正常的续传成功用例**测不出这个坑**。

---

### 坑 11:进度报成了"收到的字节数",续传直接错位 🔴

**是什么**
续传看起来正常完成了,摘要校验却失败;或者更糟 —— 摘要恰好也对上了,但文件里有一小段是错的。

**怎么来的**
底层缓存格式是**按块**记录"这部分已就绪"的。中断如果发生在某个块的中间,那半个块**不算已就绪**。

如果服务端把"网络上已经收到多少字节"当作进度返回给调用方,调用方就会从一个**服务端并未真正持久化**的位置接着传,中间那半块的数据就丢了,后面的内容全部错位。

**解决方向**
进度必须定义为"**已持久化的、连续的、可安全接着写的偏移量**",从缓存文件形态本身推导(见 FR-4)。

调用方因此最多需要重传一个块的数据量,这是**正常且预期的**,不要为了"省掉这一点重传"去引入独立的进度记录。

---

### 坑 12:内容更新了,用户却拉不到新的 🔴

**是什么**
覆盖上传了新版权重,或者往版本里追加了新文件,但用户用同样的命令拉取时,拿到的还是旧内容,或者干脆没看到新文件。清缓存后才正常。

**怎么来的**
现有下载链路会把版本标签解析成一个**快照标识**,并回给客户端。标准下载客户端**普遍假设"快照标识不变 = 内容不变"**,会直接复用本地已缓存的内容,不再重新拉取。

如果实现时把版本标签直接当作快照标识(比如恒为 `main`),那么内容变了、标识却没变,客户端就永远看不到更新。

**这个坑在逐个文件上传时一定会遇到**:传完第 1 个文件和传完第 5 个文件,版本内容是不同的,但如果标识不变,先拉过的客户端就停在了 1 个文件的状态。

**解决方向**
见 FR-5:版本标签与快照标识分离,**内容一变就产生新的快照标识**(建议由完整清单确定性计算)。

**验收**:必须构造"同一版本标签下内容变化后,标准客户端能拿到新内容且不混入旧文件"的用例。

---

### 坑 13:自研模型被磁盘清理任务删掉 🔴

**是什么**
运行一段时间后,自研模型突然下载不了了。查磁盘发现文件没了,但版本信息和文件清单还在。而且**没有任何人执行过删除操作**。

**怎么来的**
现有的磁盘清理任务在缓存超过容量限制时,会遍历缓存目录,按最久未访问 / 最早修改 / 体积最大等策略**直接删除文件**,没有任何白名单。自研模型的权重文件通常体积很大,在"体积优先"策略下是**第一批被删的**。

公开模型被删了可以回源重下,自研模型删了就**永远没有了**。而且清理只删文件不删元数据,留下的是"元数据在、内容没了"的破损状态。

**解决方向**
见 FR-9:把 `dingo-local` 命名空间的内容排除在缓存淘汰之外。

---

## 8. 非功能需求

| 项 | 要求 |
|---|---|
| **性能** | 上传吞吐不应显著低于服务器磁盘写入能力。清单维护的规模指标见 FR-3 |
| **内存** | 内存占用与被上传文件的大小无关 |
| **稳定性** | 上传过程中的任何异常中断,都不得损坏已有的、已生效的数据 |
| **兼容性** | 不得改变下载侧任何已有的对外行为(边界见 §3.1.2) |
| **部署** | 单节点(见 §3.1.3);不引入新的外部依赖组件 |
| **新增配置项** | 预期包括:上传凭证、上传接口监听地址、命名空间、上传并发上限、残留保留期限、残留清理周期。实现者需在交付文档中完整列出。**截至环 3 已落地**:`upload.token`(凭证,为空则上传接口默认关闭)、`upload.host` / `upload.port`(仅接受回环地址,非回环会被强制改回 `127.0.0.1`)、`upload.namespace`(默认 `dingo-local`)、`upload.concurrentLimit`(默认 4)、`upload.stagingRetentionHours`(默认 168)、`upload.stagingCleanupIntervalMinutes`(默认 60) |
| **可维护性** | 上传与下载共用的部分不要复制一份改改用,那会导致两边逻辑随时间漂移 |

## 9. 验收标准与测试目标

> 本节说明**要验证什么**、**可以借助什么工具验证**。**不规定测试代码怎么写**。
> 前提:§0.1 的编译基线已恢复。

### 9.1 核心验收:端到端

- 用**标准的、公开的模型下载客户端**完成端到端验证:
  - 逐个上传多个文件(**包含带子目录的文件**)组成一个仓库版本,然后整仓拉取,校验文件数量、目录结构和内容与原始目录**逐字节一致**。
  - 单独拉取其中一个文件,同样校验一致性。
- **模型和数据集两种类型都要跑一遍**(均为 HF 兼容通道下的类型)。
- **同一套用例必须在"在线模式"和"离线模式"两种服务配置下分别执行,且结果一致。**
  > 针对坑 1。**只在离线模式下测试是不可接受的**。

### 9.2 清单完整性(针对坑 3)

- 逐个上传 N 个文件(N ≥ 3,含子目录),每传完一个都做一次整仓拉取,验证**已传的文件全部都在**,数量随上传递增。
  > 只测"传一个、下一个"发现不了这个坑。

### 9.3 内容更新可见性(针对坑 12)

- 用标准客户端拉取一次,然后**覆盖上传**其中一个文件,再用同样的命令拉取,验证:
  - 拿到的是**新内容**,不是缓存里的旧内容;
  - 响应中的快照标识**变成了新的**;
  - 不混入任何旧文件。
- 向已有版本**追加**一个新文件后重复上述验证。
- 反向验证:内容没有变化时重复上传,快照标识应保持不变。

### 9.4 落盘形态一致性(针对坑 2)

- 取同一个文件,一份通过上传进入系统,一份通过正常的上游下载进入系统,**对比两者在服务器上的产物形态**,应当无法区分来源。

### 9.5 下载能力复用验证

- 用通用 HTTP 工具(如 `curl`)对上传好的文件发起**按字节区间的分段请求**,验证:
  - 返回内容与原始文件对应区间一致;
  - 响应中描述内容范围和长度的信息正确;
  - 开头一段、中间一段、末尾一段都正确。

### 9.6 完整性校验验证(针对坑 4)

- 验证下载客户端的完整性校验能通过,且**重复执行下载命令时客户端认为本地已是最新,不会重新下载**。

### 9.7 大文件与断点续传

**基础**
- 上传一个显著大于内存的文件,验证服务端内存占用不随文件大小增长。

**续传正常路径**
- 上传大文件过程中强制中断(杀进程 / 断网),验证:
  - 下载方**拉不到**这个未完成的文件;
  - 该版本中**其他已生效文件的下载不受影响**;
  - 进度查询返回的偏移量是**已持久化的**位置(针对坑 11:该值通常**小于**中断前已发送的字节数,这是正确行为);
  - 从该位置续传剩余部分能够成功生效;
  - 最终内容与原始文件**逐字节一致**,与"一次性传完"无差别。
- **多次中断续传**:同一文件中断并续传 3 次以上,最终结果仍逐字节一致。
  > 只测一次中断可能掩盖累计偏移计算的错误。

**续传异常路径(针对坑 10,必测)**

| 用例 | 期望 |
|---|---|
| 续传时声明的完整大小与绑定值不一致 | 拒绝 |
| 续传时声明的摘要与绑定值不一致 | 拒绝 |
| 续传时换成**另一个内容不同的文件**,文件名/大小/声明摘要都不变 | 完整接收后整体摘要校验失败并拒绝,**不得生成前后拼接的坏文件** |
| 起始位置**小于**可续传偏移 | 拒绝,错误信息告知实际偏移量 |
| 起始位置**大于**可续传偏移 | 拒绝(不得留下空洞) |

**残留回收**
- 验证未完成的残留在保留期内可被续传,超期后可被回收,回收不影响任何已生效文件。
- 验证反复中断不会导致残留无限累积。

### 9.8 覆盖与幂等

| 用例 | 期望 |
|---|---|
| 同一位置传完全相同的内容 | 成功,且**不重复写入**(需能观测到走了快路径) |
| 同一位置传不同内容,不声明覆盖 | 拒绝,提示需显式覆盖 |
| 同一位置传不同内容,声明覆盖 | 成功,下载到新内容,清单/文件信息/**快照标识**同步更新 |
| 向已有版本追加新文件 | 成功,不被当作覆盖,整仓拉取能拿到新旧全部文件,快照标识更新 |
| 同一仓库不同版本标签 | 各版本独立可用,互不影响 |

### 9.9 并发

- 同一文件并发上传两次,验证第二个被明确拒绝,第一个不受影响、结果正确。
- 同一文件并发发起两个**续传**请求,验证第二个被明确拒绝,不产生交错写入。
- **不同文件并发上传,验证最终清单同时包含全部文件、快照标识反映最终内容**(针对坑 8,容易漏)。
- 超过并发上限时验证被明确拒绝。
- 上传进行中查询进度,验证查询不被阻塞。

### 9.10 安全与防护

| 用例 | 期望 |
|---|---|
| **从其他机器访问上传接口** | **连接不上**(针对 §4.1,必测) |
| 不带凭证上传 | 拒绝,无任何落盘副作用 |
| 带错误凭证上传 | 拒绝,且与"不带凭证"的错误信息可区分 |
| 服务端未配置凭证时上传 | 拒绝(默认关闭) |
| **各字段**(组织名、仓库名、版本标签、仓库内路径)分别包含 `..`、绝对路径、反斜杠、盘符、控制字符 | 全部拒绝,且**确认目标目录之外没有产生任何文件** |
| 路径中间环节是指向仓库外的符号链接 | 拒绝 |
| 上传到 `dingo-local` 之外的组织名 | 拒绝 |
| 非法仓库类型 | 拒绝 |
| 未声明文件大小 / 未声明摘要 | 拒绝 |
| 声明大小超过缓存格式能力上限 | 拒绝,且原因明确 |
| 实际字节数超过声明值 | 写入被中止并拒绝,**确认磁盘上没有留下超出声明大小的数据** |
| 实际字节数少于声明值 | 拒绝,该文件不生效 |
| 完整摘要与实际内容不符 | 拒绝,该文件不生效 |

> 路径逃逸用例需要覆盖多种形式和**多个字段**,不能只测最直白的那一种。这是本功能唯一不允许"大概没问题"的地方。

### 9.11 防淘汰(针对坑 13)

- 构造缓存超过容量限制、触发清理的场景,验证:
  - 公开模型的缓存**按既有策略正常被清理**(不改变现有行为);
  - `dingo-local` 下的内容**一个都没有被删除**。

### 9.12 崩溃一致性

- 在文件生效的关键步骤处杀掉进程,重启服务后验证:看到的要么是这次上传之前的状态,要么是完整的新状态;**不出现半截元数据或"清单里有但文件没有"**。
  > 不要求穷举所有崩溃点,覆盖关键步骤即可。

### 9.13 规模

- 在**单仓库 1000 个文件**规模下逐个上传,验证总耗时可接受,并记录实测数据。
- 交付文档中给出本期支持的单仓库最大文件数。

### 9.14 回归

- 验证**现有的公开模型下载功能完全不受影响**,现有测试全部通过。
- 验证 **ModelScope 通道的行为完全未被改动**。
- 验证**磁盘清理对公开模型的既有行为未被改动**。

## 11. 已知限制(必须写入交付文档)

以下是本期**有意接受**的限制,不是缺陷。使用方需要知晓:

| 限制 | 说明 | 使用方如何规避 |
|---|---|---|
| **仓库中间状态可见** | 逐个文件上传期间,用户可能拉取到一个只包含已传部分文件的不完整仓库(例如传完第 3 个文件时,拉到的就是 3 个文件的模型) | 发布新模型时使用**新的版本标签**,全部传完后再通知使用方切换 |
| **仅支持单节点** | 内容只存在于执行上传的节点上 | 集群部署时,把自研仓库的下载请求固定路由到上传节点 |
| **上传接口仅本机可访问** | 出于安全考虑,上传接口不对外暴露 | 登录服务器本机操作,或自建端口转发 |
| **上传方无并行分片能力** | 单文件顺序上传,中断后顺序续传 | 无需规避,正常使用即可 |
| **续传最多重传一个数据块** | 中断点所在的那个块需要重传 | 无需规避,属预期行为 |
| **单仓库文件数上限** | 由实现者实测后填写 | 超大仓库需拆分 |

### 11.1 环 4 完成后的状态

以下限制只描述**当前产物的状态**,不是完整功能最终接受的限制。后续环完成后,应同步移除或改写对应条目。

| 项目 | 当前状态 | 后续归属 |

## 13. 给实现者的最后提醒

1. **始终保持编译与测试基线**(§0.1)。基线已在环 1 恢复并在环 2 保持,后续每环开始前和完成后都必须确认 `go build ./...` 与 `go test ./...` 仍可运行。
2. **先读懂现有的下载链路再动手**。这个功能 80% 的正确性来自"复用对了",而不是"写对了"。
3. **不要扩大范围**。§3.2 的清单是认真的。如果某个"顺手就做了"的想法出现,请先提出讨论。
4. **四个红色的坑决定成败**,而且它们的共同特点是**正常路径都能跑通**:
   - 坑 1(在线模式找不到)→ 必须在**在线模式**下验证;
   - 坑 3(整仓只剩一个文件)→ 必须用**多文件逐个上传**验证;
   - 坑 10 / 坑 11(续传错位与拼接)→ 必须测**异常路径**,不能只测续传成功;
   - 坑 12(内容更新拉不到)→ 必须测**更新后再拉取**。
5. **摘要是必填的,这不是可选优化**。存放位置由它决定,数据正确性也由它兜底。校验时必须**把落盘内容整个读一遍重算**,不要图省事做成边收边累加的流式哈希 —— 那样跨进程续传会算错,而且会堵死将来的分块上传(§3.3.1)。
6. **续传的进度只有一个来源:现有缓存文件本身**。一旦你开始考虑"要不要建张表记一下传到哪了",就走错路了。
7. **快照标识不等于版本标签**。内容变了就必须换标识,否则客户端永远看不到更新 —— 但这不意味着要做版本控制系统。
8. **接口复杂度的检验标准**:完整上传一条 curl、续传两条 curl。超出说明设计复杂了。
9. **实现完成后,先自问 FR-6 的判定标准**:磁盘上的产物能区分出是上传来的还是下载来的吗?如果能,回去改。
