# 本地单文件上传接口压测报告

被测接口：`POST /api/local-upload/:repoType/:org/:repo/:revision/*`（`internal/handler/upload_handler.go`）

压测工具与复现脚本：[`test/uploadbench/`](../test/uploadbench/README.md)

---

## 0. 结论速览

| # | 问题 | 实测证据 | 严重度 |
|---|---|---|---|
| 1 | 单仓库多文件上传的代价是 **O(N²)**：每传一个文件都要重写整份清单和 4 份元数据 | 4000 个 64KB 文件（250MB）写进一个仓库：耗时 87.2s、**吞吐 2.9 MB/s**、写放大 **22.5×**、落盘 3.19 GB | P0 |
| 2 | 清单缓存按 commit 键无限增长，每次上传都产生新 commit，缓存**永不命中只涨不用** | 同上场景峰值 RSS **2.84 GB**，heap profile 中 96.6% 驻留在 `ReadLocalManifest` | P0 |
| 3 | 每个请求无条件分配一块 `blockSize`（默认 8MB）缓冲，与文件大小无关 | alloc profile：`writeBodyToDingCache` 占总分配的 **53.6%**（31.2 GB / 58.2 GB） | P1 |
| 4 | 超过 `concurrentLimit` 直接 429，没有排队也没有 `Retry-After` | c=64 时 **52 次拒绝换 1 次成功**，吞吐比 c=4 掉 46%，CPU 涨 3.6× | P1 |
| 5 | `ReadTimeout: 0`，慢客户端可零成本占满全部并发槽 | 4 条 **4 KB/s** 的连接，25 秒内让 **240/240** 正常请求全部 429 | P1 |
| 6 | 每写一个数据块就整表回写 128KB 块位图；blob 定长多出 128KB 头 | blockSize=1MB 时写放大 1.13×；64KB 文件落盘 192KB（**3×**） | P2 |
| 7 | sha256 落盘后二次读盘校验 | 所有场景读放大恒为 **1.00×** | P2 |
| 8 | 同一文件并发上传直接 409，不等待、不合并 | 同文件 4 并发下 **36.5%** 请求拿到 `UPLOAD_FILE_BUSY` | P2 |

**一句话**：大文件路径是健康的（单流 276 MB/s，4 并发 462 MB/s，写放大 1.02×）；
**问题全部集中在"数据集"这类多小文件同仓库的形态上**——那里 72% 的服务端 CPU 花在元数据记账上，而不是搬用户的数据。

## 1. 实验设计

### 1.1 被测路径的先验分析

先读代码定位可能的压力点，再设计实验去证伪/证实，而不是盲压：

| 代码位置 | 猜测的瓶颈 | 对应实验 |
|---|---|---|
| `upload_service.go:235` `acquireUploadSlot` | 全局并发上限默认 4，超限立刻 429，无排队 | E2、E3 |
| `upload_dao.go:182` 第二段临界区 | 按 `(repoType, orgRepo, revision)` 加锁，锁内重建清单 + 写元数据 | E4 |
| `upload_dao.go:722` `writeEffectiveMetadata` | 每次上传重写整份清单与 meta，体积随仓库文件数线性增长 | E4 |
| `upload_dao.go:347` `hashDingCachePayload` | 内容落盘后重新读一遍算 sha256 | E1（读放大） |
| `file.go:271` `WriteBlock` → `flushHeader` | 每写一个块整表回写 128KB 位图 | E1、E7 |
| `upload_dao.go:408` `buf := make([]byte, blockSize)` | 每请求固定 8MB 缓冲 | E3、E7（内存） |
| `server/upload.go:39` `ReadTimeout: 0` | 慢/卡死的客户端会一直占着槽位 | E6 |
| `upload_dao.go:157` `tryEnterLocalUpload` | 同文件并发直接 409 | E5 |

### 1.2 实验矩阵

| 编号 | 目的 | 变量 | 固定条件 |
|---|---|---|---|
| E1 | 单流基线，定位每请求固定开销与读写放大 | 文件大小 1 / 8 / 64 / 256 MB | c=1，limit=4 |
| E2 | 并发梯度，找吞吐拐点与 429 放大比 | 客户端并发 1→64 | limit=4，8MB×128 |
| E3 | `concurrentLimit` 是不是正确的旋钮 | limit 1→32 | c=16，8MB×128 |
| E4 | **数据集场景**：大量小文件写进同一仓库 | N=1000/2000/4000；分仓对照组 | 64KB，c=4，limit=4 |
| E5 | 幂等快路径 + 同文件并发行为 | c=1 / c=4 | 8MB，同一路径 |
| E6 | 慢客户端占位（可用性） | 4 条 4KB/s 连接 | limit=4，25s 探测 |
| E7 | `blockSize` 对写放大与内存的影响 | 1 / 8 / 64 MB | 64MB×32，c=4 |
| E8 | 验证内存增长是否来自清单缓存 | cache TTL 30min → 1min | 同 E4a |

### 1.3 方法与口径

- **负载生成**：`test/uploadbench` 自研客户端，请求体按种子确定性生成、不落客户端磁盘，
  `sha256` 预先算好带在 query 里，因此测到的读写放大**只来自服务端**。
- **服务端指标**：`Win32_Process` 的 `ReadTransferCount` / `WriteTransferCount`（逻辑 IO 字节）、
  进程 CPU 秒、峰值工作集；关键场景另抓 pprof 的 cpu / heap / allocs。
- **隔离**：每个场景重启服务、清空 `repos` 目录；服务跑在 18090/18091/16060，避开开发机上已有实例。
- **重试语义**：E2/E3 的客户端遇到 429 会退避 20ms 重试同一个文件（模拟真实上传工具），
  所以"成功数"恒为 N，429 计数反映的是**为了传完这 N 个文件白跑了多少次**。

### 1.4 环境

| 项 | 值 |
|---|---|
| CPU | Intel Core 5 220H，12 核 16 线程 |
| 内存 | 31.6 GB |
| 磁盘 | YMTC YMSS2ED08B66MC NVMe SSD |
| OS / Go | Windows 11 (26200) / go 1.26.5 |
| 服务配置 | `concurrentLimit=4`，`blockSize=8MB`，`cache.defaultExpiration=30min`（除非注明） |

> **口径提醒**：压测客户端与服务端同机、走 loopback，没有网络瓶颈，因此吞吐数字代表的是
> **服务端在理想网络下的天花板**；同时两者争抢同一份 CPU，会让绝对值略偏悲观。
> 写入字节是逻辑 IO，页缓存会吸收一部分，真实机械/网络存储上的表现只会更差。

## 2. E1 单流基线：每请求固定开销与读写放大

| 文件大小 | 请求数 | 吞吐 | p50 延迟 | 写放大 | 读放大 | CPU (ms/MB) | 落盘/载荷 |
|---|---|---|---|---|---|---|---|
| 1 MB | 256 | 45.4 MB/s | 21.6 ms | **1.42×** | 1.03× | 20.32 | 1.16× |
| 8 MB | 64 | 197.3 MB/s | 41.1 ms | 1.05× | 1.00× | 4.49 | 1.02× |
| 64 MB | 16 | 259.7 MB/s | 234.0 ms | 1.02× | 1.00× | 2.47 | 1.00× |
| 256 MB | 4 | 276.2 MB/s | 899.2 ms | 1.02× | 1.00× | 2.44 | 1.00× |

**读放大恒为 1.00×**，直接印证 `hashDingCachePayload` 的设计：内容写完后整份重新读一遍算摘要，
每上传 1 字节就要多读 1 字节。大文件下这被 SSD 顺序读吸收得很好，小文件下则叠加在固定开销上。

**文件越小，单位成本越离谱**：1MB 文件的 CPU 成本是 256MB 文件的 **8.3 倍**（20.32 vs 2.44 ms/MB），
吞吐只有 1/6。21.6ms 的 p50 里绝大部分与数据量无关——这就是 E4 要放大的那个固定开销。

## 3. E2 并发梯度：`concurrentLimit=4` 是一堵硬墙

固定 limit=4，8MB×128 个文件，客户端并发从 1 加到 64（429 退避重试 20ms）：

| 客户端并发 | 吞吐 | 429 次数 | 429/成功 | p50 | 端到端 p95 | 服务端 CPU |
|---|---|---|---|---|---|---|
| 1 | 175.7 MB/s | 0 | 0 | 43.1 ms | 63 ms | 4.73 s |
| 2 | 270.0 MB/s | 0 | 0 | 56.2 ms | 81 ms | 5.36 s |
| **4** | **461.7 MB/s** | 0 | 0 | 68.5 ms | 90 ms | 4.23 s |
| 8 | 446.9 MB/s | 391 | 3.1 | 69.3 ms | 293 ms | 4.84 s |
| 16 | 441.1 MB/s | 1180 | 9.2 | 69.6 ms | 995 ms | 6.14 s |
| 32 | 392.1 MB/s | 2896 | 22.6 | 78.8 ms | 1591 ms | 7.84 s |
| 64 | **250.9 MB/s** | **6673** | **52.1** | 113.3 ms | **3062 ms** | **15.17 s** |

吞吐在 c=4 见顶，之后**不升反降**：c=64 相比 c=4 吞吐掉 **45.7%**，CPU 涨 **3.6 倍**——
多出来的 CPU 全花在收请求头、校验参数、拒绝、再收一遍上。

问题不在"有限流"，而在**限流的形式**：`acquireUploadSlot` 超限就立刻 429，
既不排队也不返回 `Retry-After`，客户端只能自旋。上传数据集时客户端普遍会开几十个并发，
这个形态下服务端会被无效重试反噬。

## 4. E3 `concurrentLimit` 扫描：默认值 4 定低了

固定客户端并发 16，只调 `concurrentLimit`：

| limit | 吞吐 | 429 次数 | p50 | 端到端 p95 | 峰值 RSS |
|---|---|---|---|---|---|
| 1 | 92.0 MB/s | 6557 | 81.0 ms | 4167 ms | 68.4 MB |
| 2 | 316.4 MB/s | 1810 | 45.6 ms | 1306 ms | 79.2 MB |
| **4（默认）** | 419.8 MB/s | 1212 | 71.2 ms | 979 ms | 102.9 MB |
| 8 | 550.0 MB/s | 575 | 107.5 ms | 502 ms | 169.9 MB |
| **16** | **618.1 MB/s** | 0 | 195.7 ms | **250 ms** | 200.9 MB |
| 32 | 622.1 MB/s | 0 | 194.7 ms | 263 ms | 293.5 MB |

从 4 提到 16：**吞吐 +47.2%，端到端 p95 从 979ms 降到 250ms（-74%）**，代价是 +98 MB 内存。
再往上（32）吞吐只多 0.6%，内存却再涨 46%——**16 就是这台机器上的拐点**。

内存的规律很干净，配合 E7 可以写成经验公式：

```
峰值 RSS ≈ 基线(约 30MB) + 并发槽位数 × 2 × blockSize
```

（每槽一份 `writeBodyToDingCache` 的 `buf` + 一份 DingCache 侧缓冲。）
所以 `concurrentLimit` 和 `blockSize` 必须一起定：`limit=64, blockSize=8MB` 就是 1 GB 常驻。

## 5. E4 数据集场景：**O(N²)，这是最严重的问题**

模拟"上传一个数据集"：把 N 个 64KB 文件写进**同一个** `repo/revision`，4 并发。

| N | 载荷 | 耗时 | 吞吐 | 写入量 | 写放大 | 峰值 RSS | 落盘 |
|---|---|---|---|---|---|---|---|
| 1000 | 62.5 MB | 13.9 s | 4.5 MB/s | 682 MB | 10.9× | 280 MB | 341 MB |
| 2000 | 125 MB | 31.6 s | 4.0 MB/s | 1848 MB | 14.8× | 805 MB | 986 MB |
| 4000 | 250 MB | 87.2 s | **2.9 MB/s** | **5631 MB** | **22.5×** | **2840 MB** | **3189 MB** |

拟合出来的增长阶：**耗时 ∝ N^1.33，写入量 ∝ N^1.52，落盘 ∝ N^1.61，峰值内存 ∝ N^1.67**。
作为对比，同样 250MB 的载荷用 8MB 大文件传只要 0.54s、写放大 1.05×。
**同样的字节数，换成 4000 个小文件，慢了 160 倍。**

### 5.1 对照实验：把文件散到 8 个仓库

同样 4000 个文件，`-shardRepos 8`：

| 场景 | 耗时 | 吞吐 | 写入量 | 峰值 RSS | 落盘 |
|---|---|---|---|---|---|
| 4000 文件 / 1 个仓库 | 87.2 s | 2.9 MB/s | 5631 MB | 2840 MB | 3189 MB |
| 4000 文件 / 8 个仓库 | **35.8 s** | 7.0 MB/s | 2246 MB | **484 MB** | 1059 MB |

文件数、字节数、并发全都没变，只是把它们分到 8 个 revision，
耗时降到 41%、内存降到 **17%**。**代价确实来自"单个 revision 的清单有多大"，而不是文件个数本身。**

### 5.2 逐文件延迟曲线

`samples.jsonl` 按上传序号分桶（4000 文件 / 1 仓库）：

| 文件序号 | 0–249 | 750–999 | 1500–1749 | 1750–1999 | 2500–2749 | 3750–3999 |
|---|---|---|---|---|---|---|
| 平均延迟 | 50.9 ms | 63.4 ms | 109.0 ms | **164.2 ms** | 80.8 ms | 88.1 ms |

延迟从 51ms 爬到峰值 164ms 后回落到 ~88ms 的平台——不是单调上升。
逐次请求的延迟被操作系统写回缓存削平了一部分；但**累计写入量、落盘量和内存是实打实超线性的**（上表）。
另外注意：即使是最开头的 250 个文件也要 50.9ms/个，而分仓对照组同期只要 18.8ms——
这部分差额来自 4 个并发请求在**同一把 revision 锁**上排队。

### 5.3 根因：pprof

CPU profile（30s 采样，累计占比）：

```
50.11%  writeEffectiveMetadata      ← 元数据记账
  41.78%    WriteDataToFileAtomic     （含每份文件一次 fsync）
  36.29%      WriteCacheRequest
  21.55%  os.Rename / MoveFileEx      （每次上传 5 次原子改名）
27.98%  materializeBlob             ← 真正搬用户数据的部分
69.30%  runtime.cgocall（系统调用）
```

**只有 28% 的 CPU 在搬用户的字节，一半以上在写元数据。**

inuse heap（1.49 GB 驻留）：

```
96.63%  ReadLocalManifest → sonic.Unmarshal   1.44 GB
```

alloc space（累计 58.2 GB，对应 250 MB 的载荷）：

```
53.63%  writeBodyToDingCache          31.2 GB   ← 每请求 make([]byte, 8MB)
26.92%  writeMeta                     15.7 GB
  9.53%   hex.EncodeToString           5.5 GB
14.46%  WriteCacheRequest              8.4 GB
 7.90%  sonic Unmarshal                4.6 GB
 0.88%  NewBitset                      0.5 GB   ← 每 blob 一份 128KB 位图
```

### 5.4 机制拆解

`writeEffectiveMetadata` 的注释说"每次上传只写固定的 3 个文件，与该版本已有多少文件无关"——
**文件个数确实是常数，但每个文件的体积是 O(N)**，所以总字节数是 O(N²)。实际每次上传要动 5 个文件：

| 动作 | 次数/请求 | 单份体积（N=4000 时） |
|---|---|---|
| 读清单（`precheck` + 第二段临界区各一次） | 2 | 512 KB |
| 写 `dingo-local-manifest.json` | 1 | 512 KB |
| 写 `revision/<commit>/meta_get.json` + `meta_head.json` | 2 | ~360 KB（`WriteCacheRequest` 把内容 **hex 编码，体积翻倍**） |
| 写 `revision/main/meta_get.json` + `meta_head.json` | 2 | ~360 KB |
| `WriteDataToFileAtomic` 的 fsync + rename | 5 | — |

N=4000 时，传一个 **64 KB** 的文件要读 1 MB、写约 2 MB、做 5 次 fsync 和 6 次 rename。

三个放大源叠在一起：

1. **每个 commit 一个新目录，永不回收。** 4000 次上传留下 12002 个元数据文件、2.44 GB
   （`api/` 目录实测），因为每次上传都新建 `revision/<新 commit>/` 并在里面存一份**完整**快照。
   代码里唯一的清理逻辑 `CleanupExpiredStagedUploads` 只管 `files/` 下的 `.uploading` 暂存文件，
   历史 commit 目录**没有任何 GC**。
2. **清单缓存只涨不用。** `ReadLocalManifest` 用 `localManifest/<repoType>/<orgRepo>/<commit>` 做缓存键，
   而每次上传都生成新 commit，所以**这个缓存永远不会命中**，只是把每一代历史清单在
   `patrickmn/go-cache`（无容量上限，TTL 30 分钟）里留够 30 分钟。驻留量 ≈ `180 字节 × N²/2`，
   实测 N=4000 时 1.44 GB，与公式吻合。
3. **小文件的定长头。** 每个 blob 带一份固定 131,108 字节（36 + 1M bit 位图）的头，
   与文件大小、`blockSize` 都无关。64 KB 的文件落盘 192 KB，**3 倍存储放大**。
   实测总落盘 3189 MB ≈ `api/` 2439 MB + 4000×(64KB + 128KB) 786 MB，账完全对得上。

### 5.5 外推（谨慎看待）

按实测的三个点外推到一个 **20000 文件（1.25 GB）** 的中等数据集：

| 指标 | 外推值 |
|---|---|
| 耗时 | ~12 分钟 |
| 峰值 RSS | ~40 GB（按 `180 × N²/2` 的闭式解算是 36 GB） |
| 落盘 | ~43 GB（载荷 1.25 GB） |

内存会先撞上 OOM，压根走不到那个耗时。**当前实现无法支撑真实规模的数据集上传**——
这不是调参能解决的，得改数据结构。

## 6. E8 验证：内存确实来自清单缓存

把 `cache.defaultExpiration` 从 30 分钟压到 1 分钟，重跑 E4a：

| 配置 | 耗时 | 峰值 RSS |
|---|---|---|
| TTL 30min | 87.2 s | 2840 MB |
| TTL 1min | 68.4 s | 2891 MB |

**峰值内存没降**。但这不能推翻结论：整轮只跑了 68 秒，go-cache 的清理周期也是 1 分钟，
最多扫过一次，绝大部分清单还在有效期内。真正的证据是 5.3 节的 heap profile——
1.49 GB 驻留里 96.6% 挂在 `ReadLocalManifest` 下，而且进程结束时
`WorkingSet == PeakWorkingSet == 2940 MB`，内存是**被持有**，不是分配抖动。

## 7. E5 幂等快路径：很好，但同文件并发会被拒

重复上传已存在且完好的文件：

| 场景 | 请求数 | 201 | 409 | p50 | 服务端写入 |
|---|---|---|---|---|---|
| c=1 | 100 | 100 | 0 | **1.2 ms** | 8.86 MB |
| c=4 | 200 | 127 | **73** | 1.8 ms | 8.94 MB |

快路径本身非常干净：8MB 文件 1.2ms 返回 `already_exists`，请求体根本没读，几乎不写盘。
断点续传和重试场景会大量受益。

但 c=4 时 **36.5% 的请求拿到 409 `UPLOAD_FILE_BUSY`**：`tryEnterLocalUpload` 对同一个
`(repoType, orgRepo, revision, filePath)` 只允许一个在途请求，第二个直接拒。
对于"超时了就重试"的客户端，这意味着重试大概率撞上还没断开的上一次请求而被硬拒。

## 8. E6 慢客户端占位：4 条 4KB/s 的连接就能让接口彻底不可用

4 条限速 4096 B/s 的上传连接（合计 **16 KB/s ≈ 0.13 Mbit/s**）占住槽位，
同时用正常速度的探测请求上传 1MB 文件，持续 25 秒：

| 指标 | 值 |
|---|---|
| 探测请求数 | 240 |
| 成功 | **0** |
| 429 `UPLOAD_CONCURRENCY_LIMIT` | **240（100%）** |
| 服务端 CPU | 0.70 s（几乎空转） |

服务端资源完全没被耗尽——**是槽位被占死了**。`UploadServer` 设了 `ReadTimeout: 0` /
`WriteTimeout: 0`，只要客户端保持 TCP 连接并偶尔吐几个字节，服务端就一直等。
按这个速率，一个 8MB 的上传要占 **34 分钟**；再慢一点就是无限期。

需要公平看待：该接口在 `NewUploadServer` 里被强制绑到回环地址（非 loopback 会被改写成 127.0.0.1），
所以这不是一个可以从公网直接打的洞。但**一个网络抖动、进程卡住或者被挂起的正常客户端，
同样会永久吃掉 25% 的上传容量**，而且没有任何机制能把它踢掉。

## 9. E7 `blockSize` 的取舍

64MB 文件 ×32，c=4：

| blockSize | 吞吐 | 写放大 | 峰值 RSS |
|---|---|---|---|
| 1 MB | 639.2 MB/s | **1.13×** | **36.0 MB** |
| 8 MB（默认） | 624.8 MB/s | 1.02× | 92.9 MB |
| 64 MB | 513.1 MB/s | 1.01× | **604.6 MB** |

`WriteBlock` 每写一个块就把整份 128KB 位图回写一次，所以块越小写放大越高：
1MB 块时 64MB 文件要回写 64 次 ×128KB = 8MB，正好是实测的 12.5%。

反过来块越大内存越贵：64MB 块下 4 个并发槽就吃掉 605 MB，吞吐反而掉了 18%。
**默认的 8MB 是个合理折中**，但这两个参数必须联动配置，见第 4 节的公式。

## 10. 改进建议（按收益排序）

### P0 — 不改就撑不住数据集上传

1. **别再每次上传都重写整份清单。**
   - 最省事、收益最大的做法：加一个**批量提交**入口——N 个文件的内容先各自落盘，
     最后只重建一次清单和元数据。把 O(N²) 打成 O(N)。
   - 单文件入口保留，但清单改成追加式日志（append-only），周期性 compact 成快照；
     或按路径前缀分片，一次上传只重写一个分片。
   - `meta_get.json` / `meta_head.json` 改成读时从清单派生（下载侧本来就有
     `ConstructBlobsAndFileFile` 这种懒构造的先例），不必每次上传都物化 4 份。
   - `WriteCacheRequest` 的 hex 编码让元数据体积直接翻倍，元数据这条路径上应该换成原样存字节。

2. **给历史 commit 目录加 GC。** 现在 `api/.../revision/<commit>/` 只增不减，
   4000 次上传就留下 2.44 GB。加保留策略（保留最近 K 个 commit / M 天），
   复用现成的 `RunStagedUploadCleanup` 定时器挂上去。

3. **上传路径别再缓存清单。** 缓存键里带 commit，而每次上传都生成新 commit，
   命中率恒为 0，纯粹是拿 30 分钟 TTL 囤垃圾。要么上传路径直接跳过缓存，
   要么把 `patrickmn/go-cache` 换成带容量上限的 LRU（下载路径也该有这个保护）。

### P1 — 明显的资源浪费与可用性风险

4. **按需分配请求缓冲。** `writeBodyToDingCache` 里的 `make([]byte, blockSize)`
   改成 `min(blockSize, declaredSize)`，再套一层 `sync.Pool`。
   单这一项就能砍掉 53% 的堆分配，小文件场景收益尤其大。

5. **429 改成有界排队 + `Retry-After`。** 保留过载保护，但让客户端能等而不是自旋：
   槽位满时进一个有界 FIFO，队列也满了才返回 429，并带上 `Retry-After`。
   实测 c=64 时现在要 52 次拒绝才换来 1 次成功。

6. **`concurrentLimit` 默认值从 4 提到 8~16。** 实测 16 时吞吐 +47%、端到端 p95 -74%，
   只多 ~100 MB 内存。文档里同时给出内存公式 `≈ 30MB + limit × 2 × blockSize`。

7. **给上传服务加超时和最小速率看门狗。** `ReadTimeout: 0` 要改；
   更精确的做法是在读 body 的循环里检测速率，长时间低于阈值就断开并释放槽位。
   另外把并发额度按 token / 来源分桶，避免一个客户端占满全部槽位。

### P2 — 值得做，但不紧急

8. **块位图别整表回写。** 按页脏写，或者对单块就能装下的小文件走一条无位图的简单格式，
   顺带解决 64KB 文件占 192KB 的 3 倍存储放大。

9. **sha256 改成写入时流式累加**，落盘后只在需要时抽查。现在每传 1 字节要多读 1 字节
   （读放大恒为 1.00×）。如果 §3.3.1 的"落盘后重算"是硬约束，至少在小文件路径上可以豁免。

10. **同文件并发别直接 409。** 让后来者等待在途请求的结果并复用（本质上就是 `already_exists`
    的语义），比让客户端拿着 `UPLOAD_FILE_BUSY` 去猜要友好。

## 11. 本次未覆盖的范围

诚实列出边界，这些结论**不**适用于下列情形，需要后续补测：

- **断点续传路径**（`start=` 参数、`UPLOAD_RESUME_*` 系列错误）完全没压到；
  `resumableOffset` 会线性扫描整个块位图，大文件下可能又是一个热点。
- **上传与下载混合负载**：本次上传服务是独占的，实际部署里 8090 的下载流量会争抢同一份磁盘和 CPU。
- **cluster 模式**：只测了 `standalone`，调度器交互的开销未知。
- **真实网络**：客户端与服务端同机走 loopback，没有 RTT、丢包、带宽限制；
  真实客户端慢下来只会让第 8 节的槽位占用问题更严重。
- **物理磁盘写回**：写入字节是逻辑 IO，31.6 GB 内存的页缓存吸收了相当一部分；
  数据集规模再大一个量级时，第 5 节的写放大会直接打到物理盘上。
- **单次运行**：每个配置只跑了一次，没做多轮取中位数，量级结论可靠，个位数百分比的差异不必当真。
