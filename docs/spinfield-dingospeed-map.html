环 0 · 链路打通

spinfield × dingospeed：谁在哪台机器上做什么

一句话：spinfield 负责"从哪读、给谁看"，dingospeed 负责"怎么存、存成什么"。 字节只走一条路——后端从本机磁盘读出来，直接推给 dingospeed，全程不经过浏览器。

整体结构与数据流

职责分工

spinfield 编排侧 · 本期主要改动
  • 用户与权限、仓库业务状态（dingospeed 完全不涉及）
  • 目录浏览与文件清单展开
  • 任务生命周期与进度：创建、状态机、失败原因
  • 读源文件、算 SHA-256（io.Copy 一行，内存常数）
  • 推字节、触发发布：N 次上传 + 1 次发布
  • 模型元信息（许可、标签、精度…）——dingospeed 不认识这些
  • 仓库与容量展示（代理 dingospeed 的接口）
dingospeed 存储侧 · 本期零改动
  • 按 DingoCache 格式落盘（不是原始文件的副本）
  • 摘要校验：收完把内容整个读一遍重算，不信声明值
  • 按 sha256 去重，命中时返回 blobReused
  • 清单合并与 commit 计算（由完整清单确定性算出）
  • 原子发布：整批一次生效，中途没有半个仓库
  • 防淘汰与孤儿回收（dingo-local 排除在缓存淘汰外）
  • 对外的 HF 兼容下载服务
一条边界必须写死：源文件的清理归 spinfield。dingospeed 对源文件只做打开、读取、关闭三件事—— 不删除、不移动、不改名。释放空间由持有者做，执行者不做。

文件分布

东西在哪谁写生命周期
源模型目录（裸权重） D:\models\… 本机磁盘 用户放置 两侧都不删，由用户自理
上传任务状态与进度 spinfield 进程内存（MemStore） spinfield 重启即丢，重新提交即可
模型元信息 环 0 只在任务对象里 spinfield 环 2 才落 MySQL
blob 内容（按 sha256） dingospeed/repos/ dingospeed 持久，排除在缓存淘汰之外
文件清单 + revision 元数据 dingospeed/repos/ dingospeed 随每次发布产生新 commit
已传未发布的暂存内容 dingospeed/repos/ dingospeed 对下载方不可见，168 小时后回收

数据流逐步

  1. 前端浏览本机目录，用户选中一个模型目录GET /admin/v1/local-fs?path= —— 原型里这块已实现，只需把假目录树换成真实返回
  2. 提交任务：模型名、版本、源目录、文件相对路径清单POST /admin/v1/model-uploads —— 不含字节，也不含摘要；后端先 stat 一遍，任一文件不存在就同步拒绝
  3. 逐文件读两遍：先算 SHA-256，紧接着再读一遍用于推送第二遍通常还在页缓存里，几乎不花代价——这是"逐文件交错"而不是"先算完全部"的原因
  4. 把这个文件的字节推给 dingospeed，声明暂缓生效POST /api/local-upload/…?size=&sha256=&defer=true —— 此刻下载方看不到任何变化
  5. 全部文件就绪后，一次性发布POST /api/local-publish/… 带完整清单 —— 整批原子生效，只产生一个 commit
  6. dingospeed 把内容按 sha256 写入 blob，重算摘要校验，同内容自动复用落盘形态与从上游下载缓存下来的完全一致，下载链路原样复用
  7. 前端每秒轮询任务快照，显示阶段与逐文件进度GET /admin/v1/model-uploads/{taskId} —— 后端自己就是搬运工，进度就是复制循环里的计数器，不需要任何回调协议
  8. 最终用户用标准客户端拉取，感知不到这个模型和公开模型有任何区别走 :8090 的 HF 兼容通道；这也是验收里"内容真的进了 blob"的第二重证据

将来拆成两台机器时，变的只有一段
