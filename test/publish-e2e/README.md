# 批量发布端到端验证

用真实二进制起一个服务实例，`curl` 走完整的上传 → 发布 → 下载链路，验证
[batch-upload-requirements.md](../../docs/batch-upload-requirements.md) 环 5 的验收项。

单元测试验证的是内部状态，这个脚本验证的是**对外行为**：客户端拿到的字节、
响应码、快照标识，以及"发布之前什么都看不到"这件事在真实 HTTP 上确实成立。

## 跑法

```bash
# 1. 准备一个独立的工作目录（不要复用生产的 repos 目录）
mkdir -p /tmp/publish-e2e/config && cd /tmp/publish-e2e
go build -o dingospeed ../../path/to/dingospeed/cmd

# 2. 放一份 config.yaml，关键项：
#    server.port: 18090   upload.port: 18091   server.repos: ./repos
#    upload.token: "debug-upload-token"        upload.publishMaxFiles: 1000

# 3. 起服务，然后跑脚本
./dingospeed > server.log 2>&1 &
bash run-e2e.sh
```

脚本自带断言，全部通过时最后一行打印 `全部通过`，否则打印失败项数量并以非零码退出。

## 必须跑两遍

**`server.online` 为 `true` 和 `false` 各跑一遍，结果必须一致。**

在线模式下系统会先向上游求证仓库是否存在，而自研仓库在上游并不存在——这正是
主文档坑 1 的成因，也是唯一一个"离线测得过、在线测不过"的失效模式。只在离线模式
下验证是不可接受的。

每次切换模式前请清空 `./repos` 并重启服务，否则上一轮的产物会让"发布之前不可见"
这类断言失去意义。

## 覆盖范围

| 段落 | 验收项 |
|---|---|
| 1~2 | 暂缓生效上传；发布前元数据与文件均不可见、磁盘上零元数据（§9.3） |
| 3 | 一条 curl 完成发布，5 个文件只产生 1 个快照标识（§9.3） |
| 4 | **等价性：批量与逐个上传的快照标识逐字符相同**（§9.1，最关键） |
| 5 | 整仓清单一个不少、逐文件内容逐字节一致（§9.2） |
| 6 | 分段下载：开头 / 中间 / 末尾（§9.5 下载能力复用） |
| 7 | 追加一批后老文件仍在、标识更新（§9.2 / 坑 批-6） |
| 8 | 覆盖：未声明时整次拒绝且标识不变，声明后拿到新内容（§9.5） |
| 9 | 发布清单含未上传文件时整次拒绝并指出路径（§9.4 / 坑 批-2） |
| 10 | 数据集类型行为一致 |
| 11 | 公开模型链路未受影响（§9.12） |

## 依赖

`curl`、`sha256sum`、`cmp`、`dd`，以及一个能解析 JSON 的 `python`。脚本会生成
一个 20MB 的随机文件用来验证跨块内容与分段下载。
